# 核心设计约定

本文记录长期应保留的设计取舍。当前命令和能力以 Skill 参考文档及 `assets/capabilities.json` 为准；新功能不能通过更新状态字段绕过实际验证。

## 1. 工作空间、被测项目与系统

Agent 打开的工作目录是工作空间，不必等同于一个被测产品。工作空间下可以有多个被测项目，项目下再区分客户端、管理端或其他系统。跨系统需求保留一个主记录，跨项目内容显式引用；两个项目使用相同需求编号时，以项目和需求的组合定位。

接手已有资料先识别入口、来源和现有约定，不因目录不标准就重建。目录和内部 ID 由 Agent 维护，用户以项目名、需求名和自然语言沟通。

## 2. 共享不意味着默认通用

共享规则、模板和模块记录来源、适用范围、版本与覆写边界。业务规则不能通过配置覆写来消除冲突。项目引用固定版本，发现共享更新时指出受影响内容，由当前任务决定何时重新验证。跨项目同名功能不自动共享业务预期。

## 3. 状态是一组事实

内容可评审、页面步骤已核实、具备执行条件、已上线、短期稳定、知识已同步、数据已恢复分别记录。“测试结束”不覆盖未修 BUG 和待上线事项。阶段概况用于理解进度；证据、产物版本与真实回执提供依据。

暂停是用户意图，断线是运行情况，等待外部输入是阻塞来源，未知写操作是需要回查的状态。它们不能混为失败或完成。只读找回进度不等于重新启动执行。

## 4. 多会话协作

每项需求有协调归属，执行任务有明确所有者、批次、场景范围、输入版本和数据上下文。并行只用于彼此独立的资源；同一页面、导图或业务对象按一致资源标识协调。

创建会话或委派需要用户授权及实际宿主能力。交接前核实旧执行者停止，核对在途操作、输入与占用；不能单凭超时抢占。工作空间锁保护短时文件写入，不声称能阻止绕开工具的其他操作者。

## 5. 长期保全

原始材料、可追溯结论、生成摘要和实际产物分开。摘要可以重建，但不能成为唯一原始证据。重要结论及时保存；新版本用新快照并保留历史，归档不删除未完成事项。

记录有格式版本、修订、前一版本摘要及校验。升级显式进行，先处理旧执行与恢复点。备份说明覆盖和排除项；恢复到新目录，核对后再激活。当前工具不提供跨机器强制互斥或自动异地备份。

## 6. 自然引导

解释目的、眼前进展和下一步，不要求用户记住内部阶段词。已有事实由 Agent 主动读取；缺失信息按影响下一步的程度补问。讨论、编辑、执行与外部写入的范围由用户当前指令和会话内授权共同决定。

用户中途提问先回答，再继续仍有效的原任务；明确暂停才停止新动作。流程复盘在分析结束、用例评审后、测试收尾时简短进行，依据本轮真实收益和问题，不发重复问卷或阻塞已授权工作。

## 7. 需求理解驱动场景

需求阶段要理解业务对象、术语、角色、状态、历史限制和本次改变。主动查 asynctest-kb；接口相关细节由 NexoFolio 补充。新成员先建立有界背景，再按当前任务深入。

澄清是否足够从用例反推：准备条件、关键输入、操作链路、预期与受影响边界能否明确表达。影响场景或判定的问题必须问清；不影响本次工作的问题保留而不无限追问。缺口只阻塞受影响的部分。

## 8. 页面取证贯穿全过程

页面取证有两项产出：可按真实页面执行的用例步骤，以及可复用的 UI 操作知识。它可以发生在分析、编写、修订、执行和复验中，不是一次性的必经关卡。

无新页面时，以现有页面与需求原文组合步骤并标明待验证；全新平台没有旧页面时允许先写逻辑用例。部署后补采并同步步骤。页面偏差先区分术语或布局变化与业务缺陷，不能一律以现状改写预期。

## 9. UI 模块的六项约定

| 设计点 | 约定 |
| --- | --- |
| 最小内容 | 稳定 ID、用途、项目/系统/环境/角色范围、前置、输入、动作、完成检查、来源与版本 |
| 划分粒度 | 按有业务意义且可独立复用的操作，如查询申请、打开详情；避免一控件一模块或整项需求一个巨型模块 |
| 复用层级 | 页面动作、组合流程与场景业务断言分开；稳定动作可组合，用例保留自身预期 |
| 复用前提 | 匹配限定范围和当前页面，未验证候选不可标作通用能力 |
| 更新方式 | 执行中沉淀有效信息，局部变化定向重采；新版本保留旧证据，不覆盖其他项目适用结论 |
| 开销控制 | 先索引和简洁回执，关键边界回读；失败再展开证据，不反复整页截图和回传源码 |

通用包提供契约和工具，不内置某个组织的业务选择器。页面证据未验证时不能为了节省 token 跳过观察。

## 10. 用例与执行

优先推荐思维导图，尊重用户格式；任何格式都保留可执行步骤。按独立场景组织，每场景从 1 连续编号；同一场景跨角色时交接真实数据并连续编号。评审直接使用完成的用例，反馈归修订，不增加 Skill 的强制评审流程。

用例围绕实际业务和控制变量，包含少量贯穿完整链路的回归。执行前核对范围、环境、版本、角色和必要数据，网络不可达不自动换环境。结果、证据、载体同步、BUG 关联和数据恢复分别核算。

## 11. BUG、复验与关闭

用例预期是缺陷判断的重要依据，但需确认其当前规则来源。明显的用例外问题可作为探索发现，不能虚增用例执行数量。失败场景与 BUG 是多对多关系，不能机械地一条失败建一张工单。

BUG 先保存预提交稿，简洁、可复现，默认严重程度和优先级 3。UI 问题至少一张真实标注截图放在结果中。提交和关闭默认采用已配置 API，未知结果先查原对象；不重复建单，不替开发先置已解决。

只收到 BUG 链接时先读工单、复现步骤、环境、修复状态及相关用例，再复现原问题并回归受影响的相邻链路。关闭需要实际复验依据、必要恢复、具体授权及关闭后的远端读回。

## 12. 最终知识

过程持续本地留存。正式上线、用户确认短期稳定后，强烈推荐沉淀业务规则、角色状态、边界和实际变化，并解释其对后续需求与交接的价值。操作日志、临时凭据和一次性失败噪声不默认成为业务知识。

写前整理具体可预览内容，遵守服务确认流程，成功后按返回引用读回。后续需求变更时维护适用范围和现行版本，保留可追溯关系，不静默累积互相矛盾的规则。
