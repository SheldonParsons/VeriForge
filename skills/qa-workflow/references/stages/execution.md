# 测试执行与证据

先读取已有用例、准备条件、项目约定和运行记录，只补会影响执行的缺口。明确系统、环境、产品版本（未知则注明）、角色、数据、范围与授权。网络不可达时保留阻塞，不自动切环境。

## 执行顺序

1. 固定用例／规则／模块版本和本轮范围，准备必要身份及数据。负例的不足权限或无数据可能正是测点，不一律当准备失败。
2. 原生 UI 按页面步骤操作；[Chrome DevTools](../integrations/chrome-devtools.md) 默认专用 headless，只有用户明确要求才显式。没有适用模块时可在授权内直接操作取证，不要求先建完整模块库。
3. API 用例关联实际请求及响应，区分 HTTP 状态和业务状态，必要时回读持久化结果。接口资料或历史报文不能当作本轮执行。
4. 检查关键身份、目标、输入实际值、跳转和业务结果；成功提示或 HTTP 200 不足以证明通过。
5. 每条结果与证据先保存，再回写用例载体并核对。标记失败保留待同步，不重跑已完成业务动作。
6. 按原约定恢复临时权限／配置和数据，核对未完成项；不要删除他人数据或覆盖后续修改。

沿用项目既有业务大脑／执行者分工，不自行新建聊天或子代理。默认顺序执行；用户授权并发且资源可隔离时从少量并发开始，按服务状态调整，不能让两名执行者同时改同一单据、页面或导图。

## 判定与记录

用例结果区分 not_run、running、passed、failed、blocked、needs_verification、skipped、not_applicable。通过要求必要断言和真实证据；跳过／不适用保留范围依据，偶现未复现不能直接通过。跨角色链路必须核对同一业务数据，后续阻塞不抹掉已观察到的失败。

`case.record` 保存本地结果；通过／失败以及跳过／不适用须关联依据快照。新扩展状态需格式 2，旧格式升级见[记录与升级](../workflow-records.md)。这些命令不执行业务或代替判断。

Mind 默认通过标 100、失败标 error，先核对真实标记键；其他状态可用实际支持的标记或备注。只更新本轮完整验证的场景，保留无关优先级。一个节点含多个必测实例时，全部通过才能标通过；局部验证不能把父节点全部改绿。

失败场景与 BUG 多对多关联，每条失败有 BUG、候选或原因；脚本错误、用例过时和环境数据问题先分流。用例外探索发现单独记录，不增加原用例通过数。UI BUG 至少一张真实标注图，见[BUG 处理](defects.md)。

## 停止、重试和接续

读操作仅在明确安全且暂态失败时按约定有界重试，默认至多一次；业务拒绝和身份不明不作暂态重试。所有写入先登记意图和派发，结果不明先回查，不能因超时再提交。

本地 `operation.prepare → operation.dispatch` 只登记；外部调用仍由 Agent 经宿主原生工具执行。实际回查后才 `operation.resolve`。没有实现的自动执行器或回调桥不得声称可用。

用户暂停时保存断点、在途操作与资源；新会话核对旧执行停止和实际状态后继续，不仅凭聊天超时重派。环境、身份或证据可靠性影响一组工作时暂停对应范围，其他独立工作可继续。

## 持续沉淀与交付

有效的 UI 新信息及时关联本轮证据，在场景或批次边界整理为页面资料／候选模块；限定条件验证后再复用。不能在活跃流程中热换实现，也不能将异常行为写成正确规则。

每组或约 3—5 分钟给可核算进度；宿主要求更短时从其要求。总范围与各状态数量对得上，重试不重复计数；BUG 数、待同步和恢复缺口另列。阶段交付见[收尾](closeout.md)，不默认增加成套报告。
