# 用例编写、评审交付与修订

强烈推荐 [AsyncTest Mind](../integrations/asynctest-mind.md)，但用户自己的格式和工具优先。任何格式都应补齐明确操作步骤，说明它们用于指导执行、复现 BUG 和修复验证。载体不支持某种编辑时如实说明，不擅自换成用户不需要的产物。

## 场景从业务理解产生

先核对规则和必要历史，按本期改动、受影响旧规则和少量完整主链路组织覆盖。每个场景应有明确条件和可判定结果，不能靠空值、长度、特殊字符等通用清单凑数量。

涉及业务流转的改动保留有代表性的完整链路。例如修改咨询单创建内容，选择创建、提交、真实角色审批到终态回查的一条链路，检查本期字段如何传递和使用。必要的实质分支才追加；不做全部组合，也不把整条链路藏在“已存在结束单据”的前置条件里。

相关旧规则缺失时返回澄清；等价场景合并需要依据，不因数量多而删掉不同业务结果。历史通过标记不能继承到新用例。

## 推荐格式

默认文件名：`{版本号}版本_{需求概述}_{作者简称}_{发版日期}.amind`。没有版本或日期时标明缺项，不把某个人的简称和日期当全局默认。

```text
需求概述
└── 需求概述（需求编号）
    └── 业务分组
        └── 具体条件及结果的场景标题
            ├── 准备条件
            ├── 操作步骤
            │   ├── 1、平台、角色、目标数据及真实页面动作
            │   └── 2、下一动作
            └── 预期结果
                ├── 1、对应操作可核对的结果
                └── 2、对应操作可核对的结果
```

每个独立场景从 1 开始编号；同一场景跨角色保持连续编号，写清平台、身份切换和同一业务数据的交接。不是固定四步，也不把整项需求压成一条二十多步流程。标题不堆冗余用例编号；稳定场景 ID 与节点映射放独立身份清单，和展示用例分别登记快照，正文方便评审讲解。新增场景不能打乱已有 ID，排序后保留“显示位置 → 稳定 ID → 场景标题 → 载体节点”关系。执行者须同时读取用例及身份来源。

使用[用例模板](../../assets/templates/test-case.md)。有真实页面信息就写 1:1 动作；未部署时明确哪些来自需求／原型或旧页面，保留待取证项。

## 交付与改动

写完即可拿去评审，不额外设置 Skill 必经评审关卡；团队实际评审要求仍保留。内容可评审、页面步骤已核对、执行准备就绪分别判断，业务预期未确定的部分不能称完整定稿。

用户增加／修改场景时，按规则、页面与关联模块定位影响，最小修订并保留原版本、场景身份和历史证据。新用例未执行，受影响旧结果须复核，不沿用旧标记。

保存后核对正确文件及内容，登记 case_set 交付物快照；Mind 写入和磁盘保存分别检查。评审反馈归入本阶段修订，简短复盘实际暴露的遗漏。

历史规则检索是编写与增补用例的一部分：根据改动查相关 asynctest-kb 条目，接口依赖按需补 NexoFolio。至少考虑少量完整业务链路和受控回归，避免只生成表面控件通用用例；执行 [历史补全策略](../context-bootstrap.md)。
