# BUG 记录与提交

依据用例预期、适用规则及实际证据判断差异；先核对环境、身份、状态和数据。确认缺陷现象不必等待完整技术根因；待确认问题也立即落本地，标明缺口。用例过时、执行错误与产品问题分开记录。

## 本地稿

本地运行器默认在 `projects/{被测项目}/requirements/{需求编号}/bugs/` 保存一 BUG 一份正文，证据登记为该需求的不可变快照；已有外部目录可映射，不能复制成两份权威稿。未关联需求保留待关联，不猜编号。跨系统问题有一份主记录及引用。

写稿前必须读取并使用[BUG 模板](../../assets/templates/bug.md)，沿用本项目已有字段；未知字段集中补问。标题按项目格式包含环境、端／功能与具体问题。严重程度及优先级默认 3／3，用户明确覆盖时采用其值；其他字段不随之默认。

在能复现的前提下尽量简洁：必要条件、最短步骤、短实际结果、明确期望。默认严格使用 `[步骤] → [结果] → [期望]`。图用 Markdown 图片语法内嵌在 `[结果]` 内、`[期望]` 之前，不能只在文末列裸路径。UI 问题至少一张真实标注图；保留原图和来源，不能用重绘图冒充实测。接口 BUG 不强制截图，保留必要请求／响应和回读。不要为减少文字丢掉关键输入、角色、顺序或状态。

账号段在步骤之前；口令只按用户明确项目约定处理，在指定本机或获授权工单中保留，不进入公开包、Git、通用交接或知识正文。没有技术归因依据时保留待归因，不凭外观猜前后端。

## 提交

先查本地关联和指定范围内已有工单，比较触发条件和问题实质，避免重复。每条失败有对应解释，多条用例可关联同一 BUG。

默认禅道 API；使用[接口约定](../integrations/zentao.md)。本地稿先准备好，按用户指定单条或已授权批次提交，已有授权不逐条重复问。方法默认不等于自动提交所有积压问题。

派发前固定正文、字段映射和附件版本。上传、创建、字段补齐和核验分阶段保存；创建结果未知先回查，拿到远端 ID 后只操作同一条。字段和正文实际回读，图片核对正式关联及保存后内容，不只看 HTTP 200、上传者缓存或成功提示。

所需截图标注或提交适配器不可用时保留本地稿及具体缺口，不能伪造附件或假装已提交。本包提供 `screenshot.annotate` 和 `bug.draft`；提交按项目实际 API 契约通过宿主工具或 HTTP 执行器完成，上传绑定协议须单独核对。

用 artifact.import 保存授权快照，再用 deliverable.set 关联 bug 产物；这些命令不向禅道写入。远端修改不能用旧稿覆盖新内容。关闭和复验见[复验](retest.md)。交付前按 [执行落盘与交付核对](../execution-checkpoint.md) 检查正文、图像登记和结果关联。
