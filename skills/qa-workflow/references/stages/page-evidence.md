# 各阶段按需页面取证

页面取证有两个目的：让用例步骤与真实页面动作一致，并积累可复用的 UI 资料。它可以发生在编写前、编写后的增补、执行或复验期间；不作为所有用例编写的硬前置。

对用户说明：“我会先核对这次需要的入口和独特操作，把真实步骤记下来，后续执行时就不用反复摸索。”

## 选择范围

先确认全部受测分组和已授权条件，查现有页面资料及适用 UI 能力，再采样缺失组件和独特链路。采样不等于执行整套用例；角色、环境或版本不同不能直接继承验证。

| 页面情况 | 处理 |
| --- | --- |
| 现有页面可用 | 保存实际入口、控件、角色与状态、数据交接和关键结果 |
| 新功能未部署 | 结合旧页面和本期需求写暂定步骤，分别标识来源及待核对项 |
| 平台首版无页面 | 基于已确认规则和原型形成可评审稿，保留操作待核对状态 |
| 后续新增场景或页面变化 | 定向补采并修订受影响步骤，不重做全部历史 |

真实页面与原型不同，先判断是操作描述漂移还是业务规则冲突。前者可据实更新步骤，后者返回澄清或记录 BUG，不能把实际错误改成预期。

## 操作与留存

遵守[浏览器接入](../integrations/chrome-devtools.md)，默认专用 headless；先核对环境、身份与允许动作，不用业务写接口替代 UI 采样。SSO、上传等自身为测点时保留实际链路。

页面资料记录来源、时间、环境／产品版本或可观察特征、角色、入口、状态、关键控件、数据标识及限制。快照只能证明该次观察，操作和业务持久化另取证。

有复用价值时按[UI 模块说明](../ui-modules.md)形成契约与实现，真实验证后登记范围。首轮验证可在已授权采样任务内进行，不能因还没有 verified 记录阻止验证；人工走通不证明新代码已通过。

取证完成后更新对应步骤、页面资料和产物引用，分别记录观察、实现、模块验证和正式测试结论。需要更换会话时保留断点及未核对范围。
