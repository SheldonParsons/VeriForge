# 需求理解与澄清

需求理解决定后续场景、操作和 BUG 预期。向用户简短说明这一点，用本次业务的具体问题澄清，不要求填写长问卷。用户直接给材料时先读已有资料，已确认背景不重复问。

可这样开场：“我先看这次改了什么，再把会影响用例的业务规则和历史依赖核对清楚。”

## 怎样建立共同理解

1. 定位项目、系统、需求、目标范围和来源版本；跨端同一需求保留一份主记录。
2. 区分需求原文、已确认历史规则、用户确认、推断、待确认事项与实际页面观察。
3. 追查支撑本次场景的概念和关系。例如测菜单需要理解角色与账号，不能只认识按钮；销售公司创建咨询单需要明确该组织与账号及数据范围的关系。
4. 有知识库时按指定项目检索适用历史，核对来源和版本；历史用例只作参考。没有知识库也可用本地资料和用户说明，查不到时保留缺口，不造规则。
5. 每次围绕少量影响判断的问题追问，说明会影响哪个场景，给具体例子，再复述结论。用户暂时不清楚时保存问题和受影响范围，继续独立工作。

正向允许不自动意味着其他条件都禁止；控制变量需要合法对照，不能用通用常识填补项目规则。相关背景理解不自动扩大为其他模块的全量测试。

## 到什么程度可以写用例

按全部受测业务分组反推：能否说清角色、数据与状态、动作、可核对的结果和依据，以及必要上下游影响。足以支持可独立判断的场景即可推进，不为了解全系统无限追问，也不只挑容易的一小部分就称理解完成。

业务预期缺失会阻塞对应场景；缺新页面标签或环境数据可以留到取证／准备阶段，不能混为同一个阻塞。用例中不写“正常”代替具体结果。

轻量维护[需求记录模板](../../assets/templates/requirement.md)：范围、概念、确认规则、问题、来源和下一步。重要结论及时落盘；需要机器状态时用 `workflow.record` 的 business、page_steps、execution 分开记录并关联依据快照。

## 变化与交接

后续规则变化只重查受影响部分，更新来源和版本；保留旧结论及当时用例依据。将问题记录为 `followup.record`，写清影响和下一步，避免换会话丢失。

分析结束做简短复盘，发现关键概念遗漏立即指出。足够支持本轮用例不等于稳定知识可正式入库；正式入库见[知识沉淀](knowledge.md)，默认等待需求完成、正式上线及用户确认短期稳定。
