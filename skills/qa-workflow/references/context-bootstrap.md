# 主动查询历史知识，补齐项目理解

历史查询是 Agent 的日常职责，不应等用户提醒“去知识库看看”。它有明确范围：为当前任务补齐会影响场景、步骤或判断的背景，避免全库无差别读取。

## 新成员第一次接入

1. 从已有工作空间和用户给的项目名定位被测项目、系统和环境。核对 asynctest-kb 与 NexoFolio 返回的真实项目身份；同名或无权限时保留待确认，不猜 ID。
2. 先读相关知识概览，建立轻量背景：核心业务对象、术语、角色、状态、主要链路和已知限制。
3. 按本次需求展开历史规则正文及其版本和来源；涉及接口的字段、枚举、权限、上下游时，查询 NexoFolio 对应环境的接口资料。
4. 持久化有用结论及引用、适用范围、来源版本和待确认项。用一小段话回报：“我找到旧规则里审批人的范围了；这次是否允许发起人撤回还没写清楚，这一点会影响用例。”
5. 新会话从本地摘要及未完成事项恢复；原规则变更、来源失效或进入新任务时，再定向刷新，不能永久把首次查询当现行事实。

两个服务都未连接时，仍可先用用户资料和本地历史继续。说明缺少哪类依据，再按需帮助接入；不能编造历史，也不让用户重新解释所有已知内容。

## 工作中的触发点

| 时机 | 主动查什么 | 何时停止 |
| --- | --- | --- |
| 需求分析 | 陌生概念、角色、状态、旧规则、关联流程 | 已能解释本次改动与验收条件；剩余问题不会改变场景或结论 |
| 编写或补充用例 | 历史边界、影响链路、受控回归 | 当前改动的控制变量明确，并有少量完整业务链路覆盖 |
| 失败调查 | 当前预期的规则依据、受影响接口、已知限制 | 足以区分产品缺陷、用例过时、数据或环境阻塞 |
| BUG 复验 | 原问题、修复影响、相邻路径 | 原复现及必要回归有明确可判定预期 |

纯格式调整、改标题等无需重新查全库。无关历史不因“可能有用”塞进上下文。

## 判定依据

- asynctest-kb 是历史业务知识来源，不是只在最后写入的仓库。
- NexoFolio 是接口知识来源；响应样本和候选整理不能直接认定为业务规则或当前实际结果。
- 分开记录原始需求、用户确认、历史规则、页面观察、接口样本、推断和未知项。
- 冲突先核对项目、系统、环境、版本和生效时间；仍冲突时只问影响用例的关键差异，不按时间自动覆盖。
- “足够写用例”的标准：谁在什么前提下做什么、哪些输入或状态改变结果、结果怎样核对、主要链路及受影响边界已明确。缺口只阻塞受影响场景。

## 本地命令衔接

`project.configure` 保存服务项目映射；`context.plan` 生成当前阶段的只读查询建议，Agent 核对宿主工具 schema 后实际调用。目录或搜索只是入口，关键正文必须读完，分页未完不能声称全覆盖。

`context.record` 保存带资料快照的结论；`context.read` 返回有界摘要及显式冲突；`context.brief` 生成项目背景概览。命令本身不调用 MCP，也不把记录状态当作知识真实性认证。最终知识写回遵循上线稳定后的 [知识沉淀](stages/knowledge.md)。
