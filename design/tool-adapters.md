## 一、首版的组织方式

Agent 负责业务理解、自然引导、场景与预期、范围和结果判断；稳定的文件校验、状态保存、调用参数、截图处理、回执及恢复使用确定性工具。继续使用现有 MCP 和本地能力，不重新实现一套 Mind、知识库或浏览器。

优先使用宿主已经开放的 MCP 调用入口。统一适配层统一的是身份、上下文、输入输出和恢复约定，不表示必须自行连接全部 MCP 服务。宿主审批、工具开关和用户停止机制继续生效；不能为减少调用次数而另建不受宿主约束的连接。

旧 UI 运行库的 `createRunner({callTool})` 可作为注入边界参考，但不能据此假定所有宿主支持 JavaScript 回调桥。首版已确定为“本地动作计划 → Agent 经宿主调用原生 MCP → 保存真实回执”，完整约定见宿主契约；有经过验证的桥时才进一步优化连续调用。自主 STDIO 连接属于独立、后续验收的运行方式，不是默认后门或 WorkBuddy 通用适配。

## 三、各适配器的最小契约

所有外部动作绑定工作空间、项目／系统、需求／任务、运行与场景／步骤、环境、工具／模块版本、目标身份引用及授权范围。秘密不进入共享契约或普通回执。输入不完整时指出真正缺口，不能从全局“当前账号”猜身份。

回执至少区分操作执行状态、实际观察、业务判定、证据、同步状态与未知写入；详细日志按需展开。外部写入派发前持久化意图和目标，回读后记录结果；失败不自动意味着写入未生效。不同工具保留原生状态和引用，不强行改造成一个成功布尔值。

### A. Mind：节点身份和保存边界

读取遵循 outline → 必要 subtree，编辑用一次批量事务或大批新增，随后保存。绑定 `windowKey`、画板与稳定节点 ID，使用实际修订保护；不能仅凭焦点、标题或数组序号定位用例。

当前 `mind_apply_node_operations` 声明有 `expectedRevision`、`operations` 和可选保存参数；本地 AsyncTest 开发源码可见 `set_markers`、`add_marker`、`remove_marker`，但没有证明开发源码与安装包字节相同。实现时仍核对实际调用支持，不能只因源码存在就认为现场标记已写入。

维护业务场景与节点的稳定映射；100／error 的展示按真实标记键核对，修改状态标记时保留无关优先级等标记。窗口内编辑、磁盘保存和用例通过分别回读，批量节点数不等于场景数。调用超时先查 `mind_get_operation_status`，用户停止或撤销控制按实际协议处理，不能重连后绕过停止。任务结束执行会话清理，不关闭用户文档。

本轮能力回执已确认 `.amind`／`.xmind` 双向磁盘转换工具可见，旧记忆中的“不支持文件转换”不再作为当前结论。转换读取已保存源文件，默认不覆盖，源文件未保存内容不参与，目标若已打开受保护；按返回 warnings 核对差异。转换能力本轮未运行，不宣称格式完全无损或已满足用户自己的用例结构。

### B. 知识库：预览、确认、回执是独立阶段

查询使用实际 `projects` 等作用域参数，盘点与读取按 opaque cursor 继续；引用来自目标项目。写入传最终正文字符串，不传本机文件路径冒充正文；当前工具说明的新增上限为 10 项，同类修改／删除上限为 20 项，完整替换为一个目标。具体大小限制和完整写入 schema 在接入时核对。

平台《确认卡、候选选择和取消》《重复、并发、过期与原子写入》说明：写入先生成预览，用户确认才提交；旧基线失效需要重新核对，单个批次为共同成功或失败，同一个确认的重放不应产生第二份变更。这是平台说明，本轮没有进行写入或故障注入验证。

后续源码核对补充：当前实现将确认绑定到用户和 MCP 凭证，设 30 分钟有效期；包装层可能先返回 pending_resolved，而不是重复返回成功。未知结果应通过 confirmation_id 关联变更记录并回读正文，不盲目重发 apply。原生表单与结构化 interaction_response 的状态映射、submit／preserve 的区别和权限／过期处理已写入知识库契约；源码不等于已部署版本，真实往返待验收。

本次宿主展开的写工具入参仅呈开放对象，因此进一步只读调用已配置服务的 MCP initialize 和 tools/list，取得 [完整输入 schema](../verification/asynctest-kb-input-schemas-20261103.json)，没有调用业务读写工具。新增为 `project + items`；局部修改为 `project + changes`（target、before_text、new_content），全文替换为 `project + replacement`；删除为 `project + targets`。target 优先使用原样 knowledge_ref，无引用时才用可唯一定位的 label。

同一写工具还支持 `interaction_response`，包含服务返回的 pending_id 与 action；schema 列出 apply／cancel／submit／preserve。它们不是 Agent 可自行代用户确认的许可；根据实际待确认回执和用户选择使用对应动作，不猜 pending_id，也不添加不存在的确认工具。用户已授权内容不替代平台原生确认，取消后停止该项写入。确认／取消往返及跨宿主恢复本轮未测试，实际宿主无法完成时交付正文及待办，不绕过 MCP 走私有接口。本次 tools/list 获取方式只用于 schema 核对，不作为脱离宿主审批的业务写入传输。

`list_knowledge_changes` 当前可见，支持项目、游标、数量及操作类型过滤；它是提交／回执查询入口，不据此承诺任意历史正文可按版本直接读取。现行知识、历史来源与本地发布快照按 3.8 关联；缺乏原生历史读取时保留本地版本及正文中的适用关系。跨项目多步写入分别登记，不能把单批原子性扩展为跨项目事务。

### C. Chrome DevTools：实例和原生交互

本机配置事实只证明专用入口已配置；本轮未启动或操作浏览器，不能将它标成运行模式验收。沿用 [headless 接入设计](integrations/chrome-devtools-onboarding.md)，保留日常浏览器和原显式配置，按任务准备专用实例、目录与身份。

当前工具声明支持显式 `pageId`、快照 uid、输入点击、脚本观察、网络和控制台读取、截图、文件上传等；适配时以实际 schema 为准，不固定别名或使用旧 uid。`upload_file` 的路径须对浏览器所在机器可见；选中文件之后还需核对页面上传结果。下载需要实际文件、完整性和业务内容证据，不能把按钮点击当作下载成功。

小型观察脚本可复用；实际页面输入、点击与被测认证、上传等仍走对应原生操作，不通过内部状态赋值或业务接口跳过 UI 测点。`evaluate_script` 当前声明可从 `sourcePath` 读取代码，但可用路径与运行位置需核对，不能假定每个宿主都共享本机文件系统。

官方 [配置说明](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)列出 headless 默认关闭、独立临时目录及指定用户目录等选项；安装时明确开启，并记录实际解析版本。官方 main 的 [package.json](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/package.json) 本轮显示 1.12.0，Node engines 为 `^20.19.0 || ^22.12.0 || >=23`；这不是当前 MCP 实际运行版本，也不是已验证的锁定版本。实施采用兼容的 Node LTS，并固定验收版本，不把 `latest` 直接写成可重复运行证据。

### D. UI 运行库：提炼机制，保留业务隔离

旧统一入口支持查询查看组合与详情读取，其他 3 项填表、审批、接单没有接入。当前 `validateRequest` 只接受已声明 read、字符串输入及全局 verified 等旧约定；运行器还把模块状态映射为 passed。新的 [UI 模块规范](ui-modules.md) 要求 read／draft／write、按范围验证、typed inputs、completed／blocked／failed／unknown，并由用例决定业务结果，必须适配后才能复用。

保留的机制包括来源摘要、固定依赖、目标 pageId 约束、原子保存回执、简洁返回和按需证据。必须改造的部分包括项目路径、目录映射、身份 bootstrap、验证适用性、操作与用例结果分离、写入恢复及数据类型。旧版仅维护每 ID 一个现行版本，还需满足新设计的版本固定与历史可追溯要求。

`runtime/mcp.mjs` 直接读取 Codex TOML 并新建 STDIO 连接，不可直接充当所有宿主的默认传输。旧业务脚本、公司平台选择器、GreeProject 登录桥和样本账号继续属于用户工作空间；不复制进通用包，也不能把旧平台验证状态带给新项目。源码移植前明确来源和再分发范围；本轮只提炼与登记，没有复制旧业务源码。

### E. 标注：固定上游核心，按需依赖

直接复用已固定的 screenshot-annotator 0.1.0 核心及 MIT 许可，见 [集成基线](integrations/screenshot-annotator.md)。Python 基础使用 3.11+；Pillow==12.3.0 和字体是标注时的附加依赖，未安装不阻塞需求分析。包内需要实际放入核心和许可证，现有打包器只打包 `skills/qa-workflow/`，仓库根 vendor 不会自动进入 ZIP。

输入为真实源图、匹配的坐标说明和标注数据；输出 PNG 与证据 JSON。外层绑定任务、步骤、环境和原图摘要，并查看标注可读性。全页或裁剪图需要对应坐标证据，未实现的转换明确不支持；不增加第二套 Playwright 浏览器。两个输出须共同核对，不能将半成品当完整证据。

### F. 禅道：协议和实例分别配置

首版纳入读取、标注图上传、创建、缺失字段补齐、关闭与保存回读。所属对象、版本和指派来自项目配置及实际对象核对；3／3 和正文约定沿用 3.6。不捆绑公司对象 ID、账号、Cookie 或实际 BUG 内容。

旧 [提单交接](https://github.com/SheldonParsons/GreeSalesCloud/blob/2cf29d0737a104ecc4224cd21a4529c63b968fb3/ui-automation/platforms/zentao/shared/bugs/submission-handoff.md) 证明特定实例中，同源已登录会话通过 REST 文件上传、同一 uid 建单后，图片正式绑定且经保存／编辑后回读及用户独立查看确认；它没有交付通用客户端，也不证明独立 Token 客户端的图片链路已通过。

先实现可选择的实例协议配置；已知 v1 同源会话 API 链路作为首个候选兼容路径，仍是 API 请求，不走正常表单创建。需要浏览器承载同源会话时也遵守 headless。独立 Token HTTP 传输作为另一个配置，必须单独验证上传与绑定，不能混用两种会话或照搬同名 uid 就认定等价。

官方检索片段给出两种不同关闭候选：[v1](https://www.zentao.net/book/api/1121.html) 为 POST `/api.php/v1/bugs/{id}/close`；[v2](https://www.zentao.net/book/api/put-bugs-bugid-close-2199.html) 为 PUT `/api.php/v2/bugs/{id}/close`。页面全文直读本轮超时，仅把官方索引作为契约候选，实际实例版本、认证、允许的状态转换仍需核对。禁止以修改真实 BUG 的方式试探哪个接口有效，也不把一种版本替换为另一种后重发。

后续已找到并核对旧工作台四条真实关闭回执：明确记录 v1 POST、multipart/form-data 的 comment + uid、单次派发、closed 和备注／附件核验。因此首个实例的历史关闭依据已补齐，详见禅道契约；独立 Token 上传绑定、当前部署权限和通用 uid 获取仍需在相应实例准备与验收时核对，不能将历史成功当成当前新执行。

实现必须覆盖：提交前固定稿件与附件摘要、分阶段操作记录、一次创建、未知结果回查、字段回读、附件绑定和绕缓存图像内容核验、授权关闭及状态回读。必要字段被忽略时补齐同一 ID，不另建单。图片独立账号可见性按首次接入／链路变化验收，真实单条结果不得继承未经验证的跨账号结论。

### G. 接口执行及可选接口知识

NexoFolio 当前公开 11 个只读知识工具，可查项目／环境、接口、字段、依赖及保留报文；历史样本不等于当前认证或实时结果。它不执行 HTTP，接入也不是接口测试的必需条件，用户提供的有效接口资料同样可用。

用户后续授权补充的 [NexoFolio 使用、Fetcher 安装与 MCP 图文](integrations/nexofolio-onboarding.md) 已具备九张导航图。外网 endpoint 与专用凭证入口有公开文档及用户截图依据；Fetcher 安装采集、MCP 配置和只读检索验收分别引导。该次公开网页取证与首轮工具盘点单独留证，不代表已配置或测试 NexoFolio 业务访问。

建议首版最小执行器支持明确的 HTTP/HTTPS 请求、查询参数、必要请求头、JSON／文本请求体、受控身份引用、超时和实际响应保存；业务断言由用例提供。批次先按依赖串行，后续并发沿用授权与隔离约定。上传等特殊接口先由专用适配器处理，未覆盖的协议、签名或编码明确列出，不伪称通用全协议执行。

认证准备、数据创建、主测请求、后续读取和清理分别记录。读取可按声明有界重试；写入未知先回查，不能因 HTTP 状态或网络超时猜测未应用。业务层效果与方法名分开判断，不能把 GET 自动当成无副作用。请求／响应的完整性、必要业务持久化和边界证据与 3.5 对齐。

## 四、必要配置按使用时机收集

工作空间归属与资料路径沿用已有记录。使用某项工具时再补齐其必要配置：被测系统与环境、角色及凭据引用、Mind 文件／节点映射、知识项目映射、禅道实例协议和对象映射、UI 目录及版本、浏览器实例与资源归属。不要求用户一开始填写全部字段。

同一工作空间可以使用多个业务项目和知识项目，不凭显示名称推断同一身份；通用规范与业务差异分别记录。连接配置和能力发现不自动扩大业务授权。现有配置只读核对后复用，缺失时按已确定的接入规则帮助配置；纯咨询或本轮适配设计不安装。

## 五、首版宿主与边界

目标为标准 Skill + 本地 Python 基础 + 宿主 MCP 调用，可在不同 Agent 中表达同一流程。首轮验证使用当前 macOS／Codex 环境；WorkBuddy 及 Windows 是明确的后续验收目标，当前不写成已兼容。实际宣称支持的组合必须有安装、工具调用、确认交互、图片展示、文件访问、暂停恢复及资料接续证据。

不把自动新建会话、模型自动选择、跨宿主后台调度列为首版完整流程的硬前置。具备相应能力且用户授权时接入；否则交接记录仍可支持用户在另一个会话继续。项目既有业务大脑／执行者分工继续沿用，不因为宿主缺自动派发就让两个会话同时操作一个资源。

首版不承诺：任意缺陷平台、任意文档格式自动回写、全协议 API 测试、自动 SSO／滑块通用登录、全平台无界面兼容、全量异地备份或全部历史资料自动迁移。用户选择自己的格式和工具时先核对已有能力，不擅自改用推荐载体或静默缩小测试范围。

| 2 | 将阶段说明和模板按需加入 Skill；扩展状态与产物映射 | 旧 0.2.1 记录可继续读取，原独立 review 状态兼容保留，新语义不污染旧结果 |

现有运行器 `case.record` 只接受 passed／failed／blocked／not_run，阶段仍包含 review；3.5 新增的状态和评审合并不能直接靠改枚举完成。实施先确定兼容读写与迁移方案，保留旧结果、来源版本、独立同步状态和未知操作。`operation.dispatch` 当前只登记，明确返回 `external_action_executed=false`，适配器必须把外部动作与回查接起来，不能将登记成功当成执行成功。

没有必要为设计盘点重复执行历史测试。本轮只检查文档、元数据与源码，下一阶段才在具体变更后跑必要本地验证；真实工具写入、故障恢复、UI 模块与宿主确认按对应授权验收。耗时、工具调用数、返回文本量和可获得的真实 token 分开计量，未实测不承诺固定提速比例。
