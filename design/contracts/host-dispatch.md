# 宿主原生 MCP 调用与本地动作计划契约 v1

日期：2026-11-03。状态：已核对旧运行库和官方宿主资料，确定首版共同调用方式；新动作计划工具尚未实现，WorkBuddy 实机和跨宿主恢复仍待验证。本契约不依赖寻找一个所有客户端都具备的 JavaScript 回调桥。

关联：[UI 模块](../ui-modules.md)、[状态与恢复](../state-contract.md)、[多会话协作](../collaboration.md)、[工具清单](../tool-adapters.md)。

## 1. 首版决定

采用“本地准备动作计划 → 当前 Agent 经宿主调用原生 MCP → 本地保存真实回执”的协作方式。本地运行器处理归属、契约、参数、固定版本、日志和恢复；宿主继续管理实际工具、权限与用户交互。Agent 根据已授权目标推进和判断业务结果。

首版不由 qa.py 自行读取各客户端配置并建立新的 MCP 连接。旧 STDIO 连接器不能作为绕过当前宿主工具限制的替代。需要无界面浏览器时核对目标 MCP 和实际实例；可见模式仍须用户明确要求。

宿主确有可验证的 callTool 桥时可以优化连续调用，但它是可选适配，不是通用工作流的前置条件。没有桥时，原生工具调用仍能执行已授权动作并落回执，不能因此退回人工点击或虚报已经统一调度。

## 2. 本地动作计划的最小数据

下面是待实现契约，字段不代表 0.2.1 已有 CLI 参数：

- 身份：工作空间、项目、系统、需求、任务、执行批次、场景／步骤和 actor。
- 版本：用例及规则来源、模块 ID／版本／摘要、实际工具契约摘要和本地 expected_revision。
- 调用：稳定 action_id、逻辑服务／工具名、已核对宿主映射、目标页面或文档身份、必要参数和真实数据来源。
- 效果：read／draft／write、UI 副作用、回读要求、允许的重试和未知写入回查方法。
- 交互与证据：等待用户或工具的状态、真实回执／证据引用、业务预期引用、是否已完成实际派发及核对。

秘密参数以受控凭据引用或临时绑定处理，不写进通用计划、Git 或普通摘要。工具没有提供原生 call ID 时保留本地动作 ID，不伪造宿主 ID。执行机和文件路径分别核对，不把模型工具、浏览器和 CLI 假定在同一台机器。

## 3. 一个动作怎样完成

1. 本地准备读取当前记录和契约，检查任务范围、材料版本、实际目标及资源归属，形成下一条可执行动作。未知页面先取证，不能把陈旧 uid 当成长期选择器。
2. Agent 核对实际可用工具映射及本次授权。用户已授权的动作不重复问；宿主或服务提出真实审批／确认时保留原流程。
3. 外部写入先登记准备及派发状态，收到本地成功回执后才调用对应原生 MCP。登记成功本身仍是 external_action_executed=false，不能报告业务已执行。
4. 保存真实工具返回与必要页面／业务回读，把其关联到原 action_id 和工具参数摘要。字段或状态不符合契约时保留原结果与具体缺口，不用包装成功掩盖失败。
5. 由模块完成检查和用例预期分别判断操作是否完成、业务是否符合预期。保存结果后再回写 Mind 等产物，并分别核对同步状态。
6. 只有当前动作及必要回查已处理，才准备依赖它的下一动作；批量可以优化宿主调用，但不能越过身份、确认、状态变化及持久化边界。

本地 prepare／record 校验本轮记录和关联，不能证明 Agent 没有在外部绕过工具执行，也不能仅凭用户填写的“成功”生成测试证据。它是可审计的协作约定，验收还需真实行为观察。

### 查询咨询单的例子

Agent 取得已核对的页面身份，调用查询动作；实际列表为空时，模块返回完整空结果，由用例判断是否应为空。存在唯一目标时再打开详情，取得实际业务标识并回读字段。连续动作可以复用模块；每次只把必要参数和结果交给模型，完整源码与页面证据留在工具侧。遇多个目标则停止该动作，不随意选第一条。

## 4. 停止和恢复

已登记派发但回执缺失时保持未知：可能未发送、正在执行或已生效。先查宿主／服务操作状态和业务目标，不重新派发。确认工具拒绝且没有执行时保留真实拒绝证据；不能把超时或新会话不存在旧记录当成未执行。

用户停止后不产生新业务动作，原操作和资源仍需按实际状态核对。新会话读取保存记录并确认旧执行者停止或资源交接，不能仅凭会话超时取得所有权。确认暂停不清除服务端已发出的操作。

知识库确认用原 pending_id 与具体预览，Mind 用原文档和修订；写入内容变化需要重新核对，不复用旧授权的具体预览来写另一份正文。宿主没有回调桥并不妨碍保存这些稳定引用；实际连接和凭证有效性仍须核对。

## 5. 宿主差异与证据

| 宿主 | 当前可据官方资料确定的部分 | 不据此推断的部分 |
| --- | --- | --- |
| Codex | 本地／项目 config.toml，STDIO 与 Streamable HTTP，环境或请求头认证，工具开关与审批配置 | 任意本地进程能直接调用宿主已连接工具、任意表单协议兼容或业务流程已验证 |
| WorkBuddy 桌面 | 官方指南提供用户级与项目级 `.workbuddy/mcp.json` 及界面配置入口；官方连接器资料区分 MCP+Skill 和 CLI+Skill | CodeBuddy Code 的 `.codebuddy` 配置等同 WorkBuddy、支持当前 Codex 的工具封装、已通过 Windows 实机验证 |

依据：[OpenAI MCP 文档](https://developers.openai.com/codex/mcp)、[WorkBuddy MCP 指南](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/MCP-Guide)、[WorkBuddy 连接器说明](https://open.workbuddy.cn/docs/connector)。仅提炼本契约相关差异；配置以实际客户端版本为准。当前不修改任何宿主设置或安装连接器。

逻辑工具映射在接入时发现，不能硬编码所有环境都叫同一个命名空间。按用户目标选择作用域并保留已有配置；工具可见、连接成功、可完成业务动作和完整恢复分别验收。

## 6. 验收与第一批实施的衔接

本地先验证动作身份与版本冲突、重复回执、结果未知、暂停和交接、受影响范围、凭据不落普通日志以及旧资料兼容。原生 MCP 调用、用户确认、真实截图／上传下载等在获授权环境另验收；WorkBuddy 与 Codex 独立记录，不继承彼此结论。

第 4 步的共同调用路线已确定，可进入阶段指引、模板、状态与动作记录的第一批实现。实际宿主桥接优化、禅道实例认证及知识库往返验收属于明确测试门槛，不再用“还没找到通用桥”无限延后本地实现。
