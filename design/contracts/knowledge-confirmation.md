## 1. 三个事实分别记录

本地正文准备完成、服务端生成待确认预览、服务端确认提交完成，是三个不同事实。记录工具返回的原始状态、pending_id／confirmation_id、目标项目、工具和操作类型、当前正文摘要、来源版本及确认选择；不将本地状态替代远端状态。

新请求与 interaction_response 不能混传。新增使用 project + items，修改使用 project + changes 或 replacement，删除使用 project + targets。后续回答必须使用原写工具及其实际返回的待确认身份，不能把新增的 pending_id 交给删除工具。

源码显示 begin_call 逐次检查 knowledge:write；resolve_pending 再核对项目权限。因此连接过、曾能写或拥有旧预览，都不意味着当前仍有权限。

## 2. 两条确认交互路径

| 服务返回方式 | Agent／宿主处理 |
| --- | --- |
| 原生表单交互 | 服务在支持的协议和 elicitation.form 能力下返回 InputRequiredResult，带 inputRequests.write_confirmation 和 requestState。宿主展示并承载用户回答；Agent 不伪造 inputResponses 或把一般任务授权当成确认点击 |
| 普通结构化结果 | 返回 input_required、pending_id、project_id、operation、question、options 和 continue_with。Agent 展示具体预览及服务选项，取得用户针对该预览的回答后，再调用同一写工具的 interaction_response |

当前源码以协议 2026-07-28 及表单能力判断第一条路径；不要求所有宿主升级到该协议，也不伪报客户端能力。没有原生表单时，已声明的交互响应路径仍可作为兼容方式，真实宿主行为需验证。

预览要让用户看到最终正文和修改范围。材料很多时以可审阅的正文及差异组织，不以一句“是否同意”替代具体内容。收到支持用户输入的状态后保存等待点；等待本身不保持进程长时间占用业务资源。

## 3. action 的实际含义

| action | 本地源码所支持的含义 | 处理约定 |
| --- | --- | --- |
| apply | 将原确认交给业务确认流程 | 仅在用户确认当前具体预览后发送；提交成功后回读 |
| cancel | 取消当前预览 | 保留取消结果，停止该项，不自动重新提交同样内容 |
| submit | 返回 needs_follow_up，要求调用方用补充信息形成新的完整参数 | input 实际必需且非空；不是提交知识的同义词，原预览没有因此写入 |
| preserve | 可能产生新的原文预览与新的 pending_id | 按服务实际提供的选项使用，重新展示新预览；不能解释成已应用或沿用旧确认 |

补充内容改变正文时，原预览不再代表新内容。服务支持时按用户修改意图结束旧预览，再准备新稿；不得留下多个可误用的预览并在稍后确认错误对象。只有 schema 可用不等于每种 action 都适用于每个预览，依据实际 options 和返回结果处理。

## 4. 凭证归属与有效期

当前 service.py 将会话身份绑定到用户及 MCP 凭证 ID，并校验写操作类型；不是仅绑定某次 TCP 连接。待确认有效期在所查源码中为 30 分钟。以上是该源码版本事实，实施不得把它写成所有未来服务永久固定规则，优先遵守实际服务返回的到期信息和错误。

换聊天或重连时，只有能找回原预览、用户选择、当前工具和同一有效凭证引用，且服务允许，才继续原交互。不能复制另一账号或已轮换凭证的 pending_id 继续应用。日志保存本机凭据引用，不保存 token 正文或利用内部凭证 ID 代替服务鉴权。

服务返回 pending_forbidden、project_forbidden 或操作类型不匹配时停止该项。过期／stale 时重新读取目标现行内容，比较是否已有提交；确认旧操作未应用后再形成新预览，新的内容与基线需要新的具体确认。不能添加无意义文字来绕过幂等判定，也不无限重试同一个过期请求。

## 5. 结果判定与未知结果

| 实际返回或观察 | 本地判断和下一步 |
| --- | --- |
| pending_id、input_required 或原生 inputRequests | 等待确认；即使旧版外层写着 completed，也不能宣布已入库 |
| completed 但有 need_info／needs_follow_up | 待补输入；不能当作写入成功 |
| 已核对的提交回执，正文与目标回读一致 | 标记本次提交及同步核对完成，保存 commit／confirmation 引用 |
| cancelled | 记录用户取消；无该项成功写入结论 |
| pending_resolved | 只说明确认已处理；可能需要核对提交或取消，不能自行解释成成功，也不再 apply |
| 超时、连接断开、结果丢失 | 保留结果未知，先按项目和 confirmation_id 查变更记录，再核对正文；不重发新建或确认 |

重要细节：平台底层有幂等语义，但所查 MCP 包装层会先拒绝非 pending 的确认。因此不能承诺“再发送 apply 一定返回第一次成功回执”。恢复路径应使用 list_knowledge_changes 的 confirmation_id、commit、trace 等关联，以及对应项目的实际正文。

查询必须保留分页与范围，找不到某条记录不等于从未写入；相同正文可能来自其他操作，不能只凭文本相同归因到本次提交。现有公开工具没有独立的任意 pending 状态查询入口，未知取消、缺少提交线索或权限不足时保留待核验，不通过后台数据库或私有接口绕过。

服务端提交、当前可读正文及检索索引可用性也分别判断。提交有回执但搜索尚未命中时，先按条目引用核对内容及索引状态，不重复新增。知识来源完整性仍由正文审阅负责，回执 verified 不证明原资料全部事实已收录。
