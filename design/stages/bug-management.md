# 3.6 BUG 记录与提交设计 v1

创建日期：2026-11-02；更新日期：2026-11-03。状态：用户已明确同意本方案，3.6 设计定稿；具体适配与实现仍待后续阶段。本轮没有创建或改写真实 BUG、上传图片、提交／关闭工单或执行复验。标注 Skill 已取得并固定为仓库内集成源码基线，未接入 0.2.1 发布包或运行测试。

## 本次确认

用户于 2026-11-03 明确要求“3.6 就按这个方案记录下来”，在既有要求上确认以下默认规则：

1. 发现差异先落本地，对照当前规则及证据区分产品 BUG、用例过时、数据或执行问题；无法判断的保留待确认。
2. 同一问题避免重复提单，允许多条失败用例关联一个 BUG，每条失败都有可追溯解释。
3. 按指定单条或批次的授权提交，不逐条重复询问；结果不明先回查，避免重复创建。
4. 提交后核对实际保存的字段、正文与图片，以及文件正式关联，不能只凭成功响应结束。
5. 复验与关闭分别记录；“复验通过后关闭”包含条件关闭授权，只要求复验则先交付复验结果。

下文为这些规则及此前用户要求的设计基线；目录字段、状态语义和 API 适配需要在实施阶段落实，不能当作当前 0.2.1 已有能力。后续确认的 [3.7 BUG 复验设计](bug-retest.md) 细化复验入口、回归范围和关闭条件，不把设计确认扩展为真实业务操作授权。

## 用户明确要求

1. 主要依据测试用例的期望与实际执行结果识别 BUG。
2. 在测试工作空间设置专门的预提交 BUG 目录。
3. 发现问题先写入本地，按被测项目、需求编号、BUG 分层管理。
4. UI BUG 至少一张真实截图，截图必须标注；接口 BUG 不强制截图。集成用户指定的 screenshot-annotator，来源为“评估 Codex 标注 BUG 截图”会话。
5. BUG 内容沿用已确认的标题、所属项目／执行／计划／版本等格式；可从已有资料获取的先读取，确实不明才询问用户。严重程度和优先级默认均为 3，除非用户明确指定。
6. 禅道提交与关闭接口已由用户说明存在，默认使用 API 完成相应操作；具体接口、字段、身份和权限在实施前按当前实例核对。
7. 支持用户提供禅道 BUG URL 发起复验，不要求先具备本地 BUG 文稿或原用例文件。
8. 2026-11-03 补充：BUG 描述在能理解问题怎样出现、能够复现的前提下尽量简洁，减少文字，优先使用真实截图及简短标注说明现象。

承接 [测试执行设计](test-execution.md) 和 [用例编写](test-case-authoring.md)。提交方式的默认值、是否已获外部写入授权、是否复验通过和是否已关闭是不同事实，不能混为一个“完成”。

## 一、从执行差异到 BUG

用例预期是主要判定依据，但先核对它来自当前适用规则，环境、版本、身份及数据满足本条条件，实际动作和结果证据可信。符合这些条件且结果不符，可以确认缺陷现象，不必等完整技术根因定位后才保存。

差异同时可能来自用例过时、错误操作、准备数据或环境／工具问题。规则存在冲突时保存待核对记录并返回澄清；不能把所有脚本错误变成产品 BUG，也不能因为还没确定前后端归属而丢掉已证实缺陷。

发现时立即落盘，证据、复现或平台字段不齐就标明待补齐，不等到所有字段齐全才记录。一次有效观察可能已足够证明现象；偶现问题保留发生次数、条件和证据，不为凑复现次数盲目重复有副作用的动作，不把后续未出现当成原问题不存在。

用例之外的明显问题作为探索来源记录，补充其预期依据及影响，不虚增原用例数。每条失败关联 BUG、候选问题或明确原因；同一问题影响多个场景可关联一条 BUG，独立触发或不同问题不只因同模块而合并。

## 二、预提交目录与本地身份

新测试工作空间采用以下逻辑结构；这是使用者的测试资料目录，不是在 VeriForge 开源源码中存放真实业务 BUG。

```text
测试工作空间/
└── bugs/
    └── <被测项目ID>/
        └── <需求编号>/
            └── <本地BUG编号>/
                ├── bug.md
                ├── metadata.json
                ├── assets/
                │   ├── 01.original.png
                │   ├── 01.annotations.json
                │   ├── 01.annotated.png
                │   ├── 01.annotated.evidence.json
                │   └── api-evidence.json       # 接口或辅助网络证据，按需生成
                └── receipts/                   # 提交、补齐、关闭、回读等操作回执
```

现有外部 BUG 目录可映射到该逻辑归属，不强制搬迁或维护两份正文。不同项目下的同号需求互不混用。未关联需求的探索问题可进入明确的 `_unassigned` 区并记录缺口，不伪造需求编号。

Agent 根据当前任务已确认归属自动建立有实际内容的目录，用户不必手工创建文件夹。目录映射不清或同号需求归属有歧义时才补问；设计阶段不初始化虚构的业务 BUG 来填满目录。

本地 BUG 编号在对应项目／需求中稳定且唯一；若采用 BUG-需求号-序号的显示方式，后续实现需原子分配或做冲突检查，多个执行者不能争同一个编号。标题变化不改身份，提交后补上平台实例与远端 BUG ID，不用远端 ID 重新创建一份本地 BUG，也不因状态变化移动整个目录导致图片引用失效。

同一跨系统或跨项目缺陷保留一份主记录，按牵头项目／主需求归档，其他受影响对象以引用关联；不能为了多平台覆盖复制成多条相同 BUG。无归属依据时先保留待关联，不凭禅道项目同名就猜本地被测项目。

bug.md 是用户可编辑主稿；metadata 保存归属、来源用例／运行／步骤、文稿版本与摘要、远端映射及流程状态，不另维护可独立漂移的第二份正文。提交时重新读取主稿，变化后旧预览或待提交摘要失效；源文本、上传和远端正文的关系保留在回执中。

不删除已经提交的本地源稿和证据。历史版本、状态和回执可追溯；合并重复、判为非缺陷或归档时保留原因和关联，不把原事实抹掉。

## 三、默认文稿与字段

以下沿用旧项目已经确认的表达方式，并将业务取值参数化。用户本次或项目自己的明确格式优先，正文应能让开发独立复现，不把全部用例、内部规则编号或长篇推理照搬进去。

### 简洁表达与截图优先

- 标题用一句话定位问题；正文只保留必要前置、最短可复现路径、实际结果和具体期望。背景铺垫、重复解释、排查过程和完整日志放在关联记录，不默认写进开发阅读的 BUG 正文。
- 步骤按 1、2、3 连续编号，数量以能够准确复现为准，不强制固定步数或字数。关键角色、业务状态、输入值、操作先后和触发动作不能为了缩短而省略；账号段及平台必需字段也保留。
- 结果优先采用简短现象描述加标注图，能从图中直接看清的信息不再用长段文字复述。标注用框、箭头和短语指出关键位置或数值，不把整段正文搬进图片。
- 涉及保存前后、不同角色／页面或状态变化时，优先用有明确顺序和说明的对比图；每张图都应增加复现或判断所需信息，不机械堆放重复截图。
- 期望尽量用简短句子写清正确的业务结果或关键值，不只写“正常”或“应修复”。截图能解释现象，但不能代替无法从画面得知的触发条件、精确输入或验收依据；需复制的测试值仍以文字提供。
- 图统一放在结果段内、期望之前，必要时以“图1／图2”关联步骤。标注不得遮挡关键证据；使用需求／原型图说明期望时明确来源，不能替代至少一张实际页面截图的要求。
- 接口 BUG 继续不强制截图，优先用简短请求要点、关键响应片段和预期差异说明，完整报文留在证据文件；不要为了图文优先把可复制信息全部变成图片。

交付前按“别人能否按这些条件复现、是否一眼能看懂实际与期望差异”检查；删除不影响理解的重复文字，补上真正缺失的条件。写作精简不改变问题判定、字段取值、证据真实性和提交授权，也不自动批量改写旧 BUG。

```text
BUG 标题：【环境-端／功能】具体问题描述
所属项目：按本项目映射
所属执行：按本轮版本映射
所属计划：按本轮计划映射
影响版本：实际受影响版本
当前指派：有依据的负责人与用户约定
严重程度：3
优先级：3
相关需求：真实编号及名称

账号：实际测试账号／角色，口令处理按已确认的项目约定
前置条件：只写复现必需的状态、配置或数据（需要时）

[步骤]
1、具体入口、目标数据与操作
2、触发问题的操作

[结果]
简短描述实际现象及必要关键值
此处嵌入已标注的真实截图，必要时使用前后对比图；接口 BUG 可用关键请求／响应片段

[期望]
简短写清有规则依据的正确结果或关键值
```

标题按项目配置包含必要的环境、端和功能，不把“客户端／管理端”强加给没有端区分的项目。若禅道要求产品、分支、模块、BUG 类型等字段，按真实契约及项目配置补齐，不把严重程度／优先级的 3 扩展成其他字段默认值。

工作空间中的被测项目与禅道的产品、项目、执行是不同对象；允许多个被测项目映射同一禅道项目，仍需核对本条需求、执行和计划的对应关系。已确认且仍适用的映射直接复用并回读，不能凭“最新计划”或名称相似猜 ID。缺字段只阻塞准备完整提单，不阻止先保存本地问题；确实无法从资料或候选中确定时集中询问。

严重程度和优先级明确写入 3／3，不依赖平台可能变化的默认值。可以据证据说明业务影响，但未经用户明确指定不自行改成别的数值。当前指派依据现象、请求／响应和项目责任映射；技术归属不明时保留待归因，不按猜测指派。

账号段置于步骤之前，截图置于结果内、期望之前。旧项目已明确要求的账号／密码写法仅在指定本机 BUG 文稿和获授权的工单正文中沿用；通用配置、VeriForge 源码、Git 回执与知识库不保存口令。其他项目默认使用账号／角色及本机凭据引用。不能为推送文稿擅自删掉用户指定内容，也不能把含凭据稿默认加入 Git，按项目约定保存可提交摘要或引用。

## 四、UI 与接口 BUG 的证据门槛

UI BUG 的可提交版本至少具备一张来自真实页面的截图及其标注副本。展示在正文中的 UI 截图均按标注规范处理，原图不可变；标注文件、参数及证据记录一同保留，提交前查看位置、文字和遮挡情况。缺图或标注失败时仍保存 BUG，标为证据待补，不宣称可提交材料齐全。

指定工具的接入见 [截图标注集成方案](../integrations/screenshot-annotator.md)。核心绘图采用确定性叠加，截图采集沿用 Chrome DevTools 的默认 headless 规则。原生截图、用户提供截图和生成式导航示意分别记录来源；生成式重绘图、合成样例和旧截图不能冒充本轮实测证据。

标注文字解释实际已观察现象或明确用户报告，不能凭外观替代业务判定。工具不会判断截图真伪，外层需关联采集时间、环境、页面、角色、场景及步骤、截图方式和原图摘要。隐私处理如确有需要，另记录处理范围并保留原始证据；当前引入的 renderer 不提供自动打码能力。

接口 BUG 不强制截图，但必须有可复现的请求方法与目标、必要参数、时间、身份引用、响应状态及业务内容、预期与实际差异；必要时补持久化结果或后续读取。HTTP 200 也可能业务失败，HTTP 错误也可能是负例预期；证据遵循本条业务规则。认证头等秘密以受控引用处理，不把“免截图”解释为免证据。接口问题若另附截图，同样注明来源并按适用标注要求处理。

## 五、去重、状态与提交授权

先检查本地关联记录及本实例相关项目／需求的已有工单，再决定新增、补充已有问题或记录复发。比较触发条件、实际现象、预期及已有依据，不仅比较标题。查过的范围如实记录，有限查询没有命中不等于全库无重复。拿到远端 BUG ID 后，所有补齐与回读继续关联该 ID，不能为修字段或图片再建一条。

至少分开记录：

- 问题判断：待核对、确认缺陷、非缺陷／用例修订，以及依据。
- 本地稿：待补材料、可提交，以及当前稿件版本。
- 提交：未提交、进行中、结果未知、已创建待补齐、保存核对完成。
- 复验：未执行、通过、失败、阻塞／待核验。
- 远端工单：当前读到的状态、读取时间和来源；关闭是否已回读确认另记。

这些是待实现的流程语义，不能直接套用现有 0.2.1 不支持的枚举。

默认先保存预提交稿；用户指定本条或本批提交后执行。若本轮已经明确授权自动提交确认的 BUG，不再每条重复请示。默认使用 API 是方式约定，不自动授权提交积压的其他 BUG、上传所有文件或关闭所有已解决工单。

## 六、API 提交、附件和保存验证

用户已说明提交和关闭 API 存在。本轮核对了旧工作台的提交说明，尚未给 VeriForge 交付通用提单／关闭客户端；具体认证方式、接口、字段和状态转换按当前实例资料及实际权限接入，不把历史对象 ID、账号或默认 Cookie 方式写成全局常量。

历史设计来源：[原工作台的 API 提交与图片修复交接](https://github.com/SheldonParsons/GreeSalesCloud/blob/2cf29d0737a104ecc4224cd21a4529c63b968fb3/ui-automation/platforms/zentao/shared/bugs/submission-handoff.md)。引用固定到源文件修订；相关经验已提炼在本文，运行 Skill 不依赖访问该旧仓库。关闭 API 的存在由用户明确说明，本轮未调用它或验证具体路由。

提交闭环：

1. 核对授权对象、当前身份、平台实例、项目字段及父子归属、去重范围、最新主稿和证据，保存本次准备版本及关联信息。
2. 通过与建单兼容的文件接口上传标注图，记录真实文件 ID、地址及源摘要。上传只是准备，不代表图片已属于 BUG。
3. 按当前实例契约将正文及图片关联信息一次创建，派发前持久化操作状态。结果不明先回查，不盲目重放；取得 ID 后只补齐这一个对象。
4. 回读标题、产品／项目／执行／计划／影响版本／需求／指派、3／3、正文和图片位置，逐项比较，不能以 HTTP 200 或请求中有字段认定已保存。
5. 核对图片正式关联和正文渲染；保存后及重新读取工单后绕过客户端缓存读取实际图片内容，核对类型、可解码性、尺寸及适用摘要，避免“HTTP 200 返回 HTML 错误页”。
6. 区分上传者可见、服务器可读及有权查看者独立账号可见。没有接收方验证就明确未验证，不复用上传者 Cookie 冒充他人验证，也不通过公开文件或关闭鉴权解决。

每条工单完成字段、文件关联和保存后／重新读取后的图片核验；首次接入、上传链路或权限变化、用户反馈别人看不到时，再重点安排有权访问者的独立可见性验证。已有路径验证可以作为范围明确的基线，不能写成本条已跨账号亲测。若用户本轮明确要求接收方验收，缺该项就保留未完成，不为每条普通提单无条件重复要求同事手工确认。

旧项目实证提示：REST 文件上传与同一会话／同一 uid 建单的链路可正式关联图片；旧编辑器上传与 REST 建单混用曾导致保存后文件不可读。该修复经验用于适配核对，不保证所有禅道版本相同。本实例也曾忽略创建请求中的计划字段，需要对已有 BUG 进行 API 编辑补齐并回读；这种真实编辑历史应如实说明，不能重复创建或声称一次写齐。

API 字段或权限不足时保存已取得的 ID 和未完成项，优先在原授权内使用允许的 API 补齐；不能换高权限账号或重放受限接口。需要其他方式时先说明缺口并按用户要求及权限处理，不默认改为 UI 创建；凡使用 Chrome DevTools，仍遵守 headless，显式模式须有用户明确要求。

本地图片引用在提交时转换为实际上传后的富文本图片，不把本机路径、Base64 或下载链接当正文截图。用户指定图片放在结果中，提交后再核对位置。原图未变化时可比对源摘要；平台有明确的图片转换时需核对转换后的有效内容并记录边界，不能忽略图像差异或伪造相同哈希。

提交回执至少保留本地 BUG 身份、当前稿件及附件版本、目标映射、操作阶段、远端 ID、字段／图片核对结果和未完成项。可提交稿后来变化或远端已被人修改时，先核对差异，仅更新本次授权内容，不用旧稿覆盖用户修复。

## 七、BUG URL 复验与 API 关闭的衔接

用户说“复验这个 BUG”并给出 URL，或在明确复验上下文只贴链接时，直接识别目标，不要求重新提供整套需求背景。意图确实不明时只补问必要意图；链接和工单正文不是额外操作授权。

与后续复验设计衔接的入口流程：

1. 解析平台实例及 BUG ID，核对允许访问的主机和当前身份，读取最新正文、附件、状态、修复说明及关联需求；不把一个实例的凭据发到其他主机。
2. 查本地远端映射，已有记录直接关联。没有本地稿时建立远端来源记录和本次复验入口，不再创建远端 BUG；需求未关联时保留缺口，不乱挂最近需求。
3. 从现有资料补齐实际被测环境、部署版本、账号角色、数据和正确预期。复验原问题及受影响的必要范围，缺项按 3.5 处理，不将开发标记“已解决”当作通过。
4. 保存实际复验结果、证据、仍未覆盖部分和关联用例状态。失败或阻塞不自动关闭；重新激活等其他状态变更按其权限、接口能力和授权处理。
5. 默认以 API 关闭，但只有具备本次关闭授权和适用的关闭依据才执行。只要求复验不自动等于授权关闭；用户已明确授权本批“复验通过后关闭”时不重复逐条询问。关闭后重新读取状态、关闭人／时间及必要说明，结果不明先回查，不盲目重发。

关闭前核对当前状态及接口允许的转换；不能为满足关闭接口的前置条件擅自替开发标记“已解决”，或用旧工单全文覆盖新内容。采用最小必要更新并保留前后状态。需要重新激活时核对其真实接口和相应授权，不把关闭接口当通用状态修改器。

已关闭工单仍可按用户要求复验，结果作为新批次保存；仍已关闭且无需状态变化时不重复调用关闭接口。若发现复发，保留本轮证据并按授权处理激活或反馈，不另外创建同一缺陷来绕过状态流程。

用户明确只要求关闭某条，并说明人工已经验证或其他关闭原因时按其范围处理，记录依据来自用户，不伪称 Agent 亲自复验。没有实际关闭回执不报告已关闭。原问题、相关回归及关闭条件见已确认的 [3.7 设计](bug-retest.md)，本节维护与提单流程的衔接。
