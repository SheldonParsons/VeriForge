# 3.8 上线后最终知识沉淀设计 v1

创建日期：2026-11-03。状态：在此前完整方案与下一步安排之后，用户回复“可以，按照你的做”，据此记录 3.8 设计基线并继续 3.9。实际知识库适配和业务写入未实施，本轮只维护设计资料。

本阶段让下一位同事或 Agent 能找到业务含义、现行规则、适用范围和变更来源。承接 [需求分析的过程记录与入库时机](requirements-analysis.md)、[共享内容](../shared-resources.md) 和 [长期保全](../data-lifecycle.md)。知识正文是用户的业务产物，不写入 VeriForge 的通用 Skill 源码或发布包。

## 一、沉淀内容与边界

围绕业务主题整理能支撑后续理解、用例设计及缺陷判断的稳定结论：

| 内容 | 咨询单示例中的问题 |
| --- | --- |
| 概念及关系 | 销售公司、创建人、审批人是什么，与咨询单如何关联 |
| 角色与权限 | 谁可以创建、修改、查历史，在什么条件下允许 |
| 流程与状态 | 驳回、重新提交、审批结束后分别如何处理 |
| 具体规则 | 什么动作产生历史，包含哪些内容，如何展示 |
| 例外与兼容 | 无历史时如何展示，旧单据是否适用或补齐历史 |
| 本期变化与来源 | 改了什么，从哪个版本生效，依据哪项需求和确认记录 |

这些问题用于识别有用知识，不要求每个主题机械填写全部栏目。只写真实确认的内容，不为凑齐结构编造规则。既有概念已有适用主条目时引用，不重复写一份定义。

已确认规则、实际验证覆盖与已知问题分别说明。测试观察可支持结论，但不能把页面异常写成允许行为；历史偶尔缺失应保留为已知问题，不能写成业务允许缺失。待确认事项、临时假设和未上线规则留在过程资料，不能混入正式现行规则。

正文使用易读的 Markdown 文本，保留足够语境，使离开原会话的读者仍能理解。完整聊天、全部用例、运行日志及测试账号口令不照搬进知识正文；必要来源以稳定引用和版本关联。页面定位、等待条件、操作函数及运行证据继续由 UI 模块与测试资料维护。

### 咨询历史的正文示例

以下仅假设最终已确认相应规则，不代表对真实 71652 规则的再次核验：

> 项目技术咨询单：选型需求修改与历史查看
>
> 适用范围：非标产品选型咨询、技术咨询；客户端与管理端。
>
> 咨询单被驳回到创建人后，创建人可以修改选型需求。重新提交后，原选型需求保留为历史，查看和审批时能够查阅。
>
> 正式正文还需按已确认结论说明历史生成时机、包含字段、展示顺序、可见角色及旧单据处理，并注明需求来源和实际生效版本。

示例最后一段是撰写说明，不得原样作为完整知识提交。缺少影响理解的结论时保留缺口，不用“符合预期”替代具体规则。

## 二、正式入库时机

过程中的重要理解及时保存在本地，候选知识可持续整理。正式写入现行知识前核对：

1. 本期需求工作已经完成。
2. 已正式上线，有用户说明或可靠发布记录为依据。
3. 用户确认短期稳定。
4. 拟入库正文、目标知识项目及变更范围明确，具备相应写入授权。

测试通过、BUG 关闭、计划发版日期已到，不能单独代替上述条件。短期稳定允许后续通过新需求继续演进，不要求用户承诺永久不变。测试结束但未上线时交付本地候选文本，并将最终入库保留为待办。

用户明确了事实和相应写入范围后直接沿用，不反复要求确认同一项；工具自身预览与确认要求照常遵循。用户明确要求提前保存特定内容时，按其实际指令处理，并保留真实阶段和适用状态，不将未上线内容冒充现行知识。

## 三、自然引导与可选接入

用户可能说：

> 这期已经上线了，短期不会再调整，帮我把知识整理一下。

Agent 可回应：

> 我会把这期最终确认的业务规则整理出来，并和知识库已有内容对照。建议同步到 asynctest-kb，后续分析相关需求时就能先找回背景，减少重复解释，也方便其他同事接手。我先给你看新增和修改的内容。

强烈推荐 asynctest-kb，并结合当前主题说明复用、交接、发现回归范围和追溯变化的收益。未接入时复用 [已有接入指引](../integrations/asynctest-kb-onboarding.md)，帮助用户取得 MCP 信息，由当前 Agent 适配自身宿主；不默认用户使用 Codex。已有连接可用就直接使用，不重复索取配置。

连接不是写入授权，也不是开始其他阶段的硬门槛。用户暂不接入时交付本地最终文本并注明未同步，不反复催促，也不因此否定测试成果。推荐在工作会话得知上线、收尾或用户查询时触发；没有自动化时不承诺上线后自动醒来或通知其他会话。

## 四、读取、对照、写入与核对

1. 核对目标项目身份，按业务主题读取相关现行知识及必要历史，检查适用范围和来源。遵循实际工具的分页及完整性提示；有限检索无结果不等于整个项目没有相关知识。
2. 整理新增、修改、保持不变和不再适用的内容，给出具体差异及最终正文。原则上按业务主题维护主条目，需求编号作为变更来源，不每期新增一份相似正文。
3. 核对本次授权，向用户补问真正影响知识正确性的缺口，不要求重新审阅整段聊天。已有明确写入授权时在其范围内继续，MCP 要求预览或确认时使用实际流程。
4. 写前重新核对目标现行内容；其他会话已修改时检查差异，不能用旧稿直接覆盖。按授权写入后回读项目归属、条目及保存正文，确认与目标变更一致。
5. 本地保存这次正式正文及来源版本、目标条目引用、写入范围和同步结果。已成功、待处理、失败和未知结果分别记录；未知结果先查询，避免重复新增或覆盖。

本地正式稿是本轮发布快照，服务端条目用于后续读取；明确两者的版本关系，不维护两份各自随意变化的现行正文。后来再次更新时先核对当前权威来源，保留每次已发布内容与回执。

条目历史、版本字段、原子变更及跨条目事务是否由 MCP 提供，留到工具适配阶段按实际能力核对。工具不支持的关系可用正文标识、稳定引用及本地版本记录表达，不能宣称平台已经具备原生审计或并发保护。

完成依据为获授权范围内的正文与目标均已核对、写入成功并回读确认，相关引用与版本已保存。部分写入成功只能报告部分完成；没有接入时报告本地最终文本已保存、服务端未同步。知识写入不是整个需求测试通过的证据。

## 五、后续需求变更

采用业务主题维护现行知识，需求记录保留变化来源。用一个假设例子说明：X 版咨询历史只包含文字，Y 版要求把附件也纳入历史。

| 阶段 | 维护方式 |
| --- | --- |
| Y 版分析和测试期间 | X 版知识保留其适用范围；Y 版新要求记录在新需求资料中，注明未正式生效。本轮测试使用已确认的 Y 版规则，不能因为知识库还是 X 版就认定新行为错误 |
| Y 版正式上线并确认短期稳定 | 按授权更新咨询历史主条目，明确新范围、生效版本和来源需求；保留 X 版历史依据及替代关系 |
| 旧单据兼容性未明确 | 保留缺口，不能自行认定旧单补齐附件或完全不受影响 |
| 后续查询与接续 | 按目标环境、版本及业务对象选择适用规则，能回答现行行为，也能追溯当时的测试依据 |

变更时核对已知引用的项目、需求与用例，区分已核实影响和候选影响。标出需要复核的部分；修改用例或执行回归沿用对应授权。历史测试结果继续保留当时依据，不能随知识更新改写为按新规则通过。

两类变化不必等待下一次发版：原知识误写，核实依据后按授权及时更正并保留原因；已上线功能回滚，按事实修正适用状态并保存回滚来源。尚未稳定的新结论留在过程记录，不凭一次观察改写业务规则。

## 六、共享、长期保留与交付

多项目或跨端共用的业务规则保留一个主条目，明确适用范围和各端差异，通过引用关联；不因分属不同知识项目就长期维护多份相同正文。目标映射不清时只澄清归属，不自动合并或迁移用户的知识项目。

原始资料、确认来源、正式版本和变更关系保持可追溯。主题索引用于快速定位，按需展开相关历史；不能为减少上下文删除唯一来源或只保留摘要。外部知识同步与备份恢复分别记录，服务端成功不能证明全部资料已有可恢复备份。

正式交付为最终知识正文及简短同步结果，不默认增加成套报告。例如：

> 本次更新了“咨询历史”规则，补充附件范围和生效版本，保留旧版说明；新增一条旧单据兼容规则。正文已同步并回读确认，条目入口和本地版本已保存。

上述为话术示例，实际数量和内容以本轮证据为准。阶段收尾与后续待办见 [3.9 收尾与复盘](closeout-retrospective.md)。具体业务适配和真实写入仍按后续实施与验证安排推进。
