# 3.9 收尾与复盘设计 v1

创建日期：2026-11-03。状态：用户同意按提出的四项方向推进，由 Agent 据此收口设计：正式交付、真实完成情况、交接与恢复、基于证据的持续改进。以下为设计基线及说明例子，未进行真实测试收尾、归档、数据清理、提单、知识写入或消息发送。

承接 [测试执行](test-execution.md)、[BUG 复验](bug-retest.md)、[最终知识沉淀](knowledge-consolidation.md)，并沿用 [状态与恢复](../state-contract.md)、[多会话协作](../collaboration.md) 和 [长期保全](../data-lifecycle.md)。阶段收尾可在上线前发生，最终知识沉淀仍遵守自身条件。

## 一、何时进入与怎样回应

用户说“这轮测完了，整理一下”“这期先到这里”“交给同事继续”，或已授权阶段完成后，Agent 先读取实际任务范围和证据，区分本轮执行结束、暂停、交接与整个需求结束。意图清楚则直接整理，不发长问卷；确实会改变后续工作时才补问。

可以这样回应：

> 我先核对这轮实际测了哪些内容、还有哪些问题，再把用例、证据和下一步整理到需求入口，方便你或其他同事继续。

纯粹询问状态不自动结束任务；用户说暂时停下时保存断点，不把暂停改为通过或全部完成。本阶段不自动启动未经授权的补测、修复、提交、关闭、上线、知识写入或向他人发送消息。

## 二、正式交付保持轻量

默认围绕三类用户产物：

1. 本次适用的正式测试用例及其准确执行标记，注明当前版本和实际位置。
2. 本期知识内容及真实状态：候选文本、最终文本、未同步、部分同步或已回读确认。未达到 3.8 条件时继续保留待办。
3. 用户本轮明确指定的其他产物，例如测试总结、点检 Markdown 或任务表更新；按其范围处理，没有要求不自动生成或写入。

将结论、产物入口、未完成项及下一步更新到现有需求入口或工作空间约定记录，不另造多套重复报告。运行记录、BUG、截图、知识同步和恢复记录各保留原权威位置，以引用连接；实际有内容时才生成相应记录。

交付前核对目标文件和关键证据存在、版本对应、图片与正文关联可找到，外部写入有真实回执。仅有文件路径、旧导图标记或外部 URL 不能替代读取核验。无权限或工具无法核对的部分注明边界，不为了完整报表编造结论。

## 三、完成情况分开说明

至少区分本轮执行覆盖、缺陷处理、正式上线、知识整理／同步、临时资源恢复和交付接续。具体状态字段在实现阶段落实，不把这些语义直接套进 0.2.1 不支持的枚举。

本轮数量采用 3.5 已固定的统计口径，明确场景或执行实例、版本、环境与时间。通过、失败、阻塞、未执行等与总范围可对上；重试不重复计数，探索发现不虚增用例。范围经授权变化时保留原范围、调整依据和未覆盖部分，不用缩小分母掩盖遗漏。

失败场景与 BUG 分别统计并关联，多条失败可能对应同一 BUG。每条失败有问题或解释，未提交、已提交、修复待复验、已复验和远端关闭按实际事实记录，不能为了收尾批量关单或把尚未复验的场景改为通过。

本轮计划操作已执行完毕，可以报告“执行结束，存在失败”；若仍有阻塞或未执行，就报告实际进度和剩余项。测试结果不代替发布决定；有遗留问题时说明影响和已知处置，风险是否接受及上线安排按用户或团队既有决策，不由 Agent 擅自决定。

## 四、例子：测试结束，仍有一条 BUG，尚未上线

以下数字与对象为设计示例，不是实际项目统计。

假设本轮范围共 20 个场景，18 个通过、2 个失败；两条失败都关联同一个历史显示 BUG。用户说“这轮先收尾，开发修完后再验证”，当前未正式上线。

可这样交付：

> 本轮 20 个场景已执行，18 个通过、2 个失败，失败均关联同一条 BUG。当前仍待修复，本轮未关闭该 BUG。用例标记和证据已保存；知识候选稿已整理，尚未正式上线，暂未写入知识库。下一步在修复部署到 QA 后复验原问题及必要回归。

实际登记的后续事项包括修复部署依据、需复验的场景与 BUG、数据和账号角色引用、上线及稳定确认后的知识入库。已有负责者或联系对象沿用；未知就注明，不擅自给同事派活或发消息。

若这 20 个场景中还有 2 个因环境阻塞未能执行，就应改为说明实际已执行数量与 2 个阻塞，不能继续使用“20 个均已执行”的话术。因时间预算停下也同样保留未执行项。

后续用户说“修复上 QA 了，继续”时，先核对部署与最新工单，沿已保存范围进入 3.7，不重新跑整个需求。只有重新完整执行通过的场景才更新结果；新结果追加，原失败证据保留。上线并确认稳定后按 3.8 整理和同步最终知识，记录逐项完成情况。

## 五、恢复、交接与长期保留

检查本轮实际创建或改动的测试数据、临时权限、配置、文件和资源占用。按原约定恢复，并核对当前状态，不能覆盖其他人的后续修改；需要保留复现数据时注明用途与后续处理条件，不为收尾批量删除唯一证据或业务数据。恢复失败或未授权处理的部分保留明确待办。

收尾前核对仍在执行的任务、未知写入和已派发未回读的操作，不将聊天结束当成执行者已经停止。沿用既有任务责任和资源协调规则；没有宿主能力时记录不确定状态，不虚报已停止其他会话。

接手入口保留项目／需求身份、实际阶段、已确认范围与来源、产物和运行记录、遗留问题、未知操作、恢复缺口和下一步条件。凭据正文保留在约定的受控渠道，交接使用引用，不复制到通用文档。换会话先核对当前状态，复用已验证结果和已有材料，不依赖旧会话全文，也不因标记同步失败重放业务操作。

归档按现有项目约定和用户范围执行，只改变默认活跃视图，不删除源材料，不消除遗留 BUG 和待办，也不把归档作为需求通过证明。活跃引用、外部导图和仓库外图片仍需可定位；不为整理目录盲目移动文件导致断链。

本地保存、Git 提交与远端同步、外部平台写入、独立备份和恢复验证分别说明。收尾只报告本次实际检查过的范围与缺口，不宣称全量已备份或永不丢失。原文、正式版本和关键证据长期留存，索引用于按需读取，避免为节省 token 丢弃来源。

## 六、基于本轮证据的复盘

需求分析结束、用例评审完成和测试收尾时进行简短复盘；基于本轮实际问题，不重复长问卷，不阻塞已授权的下一步。没有新增问题时如实注明。

每个值得保留的发现说明实际现象及证据、对理解／执行／交付的影响、建议修改和适用范围。只提出有价值的少量改进，不为了凑数量列泛泛建议，也不把初始框架当成已经验证的最佳实践。

例如同一查询入口反复采样且步骤一致，可以提出补充对应 UI 能力和适用验证，减少后续重复读取；某个概念没有解释导致场景遗漏，应回补规则及受影响用例，并评估澄清指引。不能在缺少时间或 token 计量的情况下声称已提高固定百分比。

本需求发现保存在需求记录中。跨需求通用规范的变更由负责治理的会话或明确负责者综合评估，按已有授权更新并留版本；多个执行者不同时改写同一通用规则。用户明确要求修改通用规范时按其范围推进，已授权的具体修正不重复索取确认。

严重的证据缺口、关键业务漏测或规则冲突在发现时立即指出，不等收尾。复盘中整理后续改进不自动授权额外测试、重写所有历史用例或修改知识库。

## 七、收尾完成依据与后续

本次约定范围的结果有依据、交付入口可用、遗留事项有明确状态与下一步、恢复情况已核对、简短复盘已记录，即可完成这次阶段交接。整个需求是否结束仍按其范围和未完成项判断；没有完成的工作不会因阶段收尾被清零。

3.8 与本设计记录后，第 3 步业务环节设计基线齐备。下一步为第 4 步工具与适配范围核对，再进入实现、必要本地验证、完整流程验证和获授权真实试用。本次没有实现新运行器、安装依赖、启动真实业务测试或修改既有发布包。
