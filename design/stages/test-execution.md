# 3.5 测试执行设计 v1

日期：2026-11-02。状态：用户授权“你来定吧，用你觉得最佳的决策”，Agent 据已确认边界对剩余执行规则决策定稿，形成实施基线；不表示用户逐字段审阅或真实效果已经验证。本轮只设计，不访问真实环境、不执行用例、不安装工具、不建立执行会话、不提交 BUG。沿用 3.5 编号，原 3.4 独立评审环节已并入 3.3 编写与修订。

## 本轮决策摘要

| 事项 | 默认规则 |
| --- | --- |
| 准备与数据 | 先读既有资料和约定，只补影响动作或判定的缺口；固定批次与用例依据，合法只读数据优先复用，可变数据隔离，临时配置有恢复依据 |
| 分工与并发 | 默认单执行者顺序执行；继承项目分工，明确授权并发且资源可隔离后从 2 路起，默认上限 4，按环境和任务预算调整，不自动创建代理或会话 |
| 结果与同步 | 业务断言决定场景结果；每条先持久化结果及证据，再回写用例，业务结果、BUG、标记同步和恢复状态分开 |
| 异常与恢复 | 局部阻塞不阻断其他独立任务；有界只读重试，未知写入必须先回查，接续核对版本、现场和原执行者状态 |
| 结束交付 | 核对范围与计数、失败关联、证据、待同步及数据恢复，交付实际结果和未完成项；任务收尾不等于全通过或全部 BUG 已修复 |

既有明确要求继续有效：Chrome DevTools MCP 强推荐，默认 headless，仅用户明确要求才显式；工具缺失时在实际接入阶段帮助安装；执行中持续积累有来源的页面资料和经验证的 UI 能力。实现与真实验收等待所有业务环节设计完成后的相应授权阶段。

## 目的与继承边界

目标是将已授权范围内的用例执行到底，取得可核对的业务结果，同时让用户知道进度、问题和下一步。执行以业务规则及用例预期为判定依据，以实际页面或接口结果为事实，不以工具成功代替业务通过。

继承 [用例编写](test-case-authoring.md)、[按需取证](page-discovery.md)、[UI 模块规范](../ui-modules.md)、[状态恢复](../state-contract.md) 和 [多会话协作](../collaboration.md)。执行顺序、交互及状态规则按用户本轮委托定稿；不把旧工作台的特定模型、账号、BUG 字段或单次任务的时长／并发预算推广成所有项目的固定配置。

用户明确的通用工具要求已固定：强烈推荐 Chrome DevTools MCP，使用它的所有浏览器调用默认 headless，仅用户明确要求时才显式执行；未安装时由 Agent 帮助安装和接入。详细规则见 [接入与隐式调用](../integrations/chrome-devtools-onboarding.md)。设计定稿不是本轮实际安装或测试的授权。

实际团队要求评审通过才能测试时沿用该要求；VeriForge 不另外强加一套独立评审流程。用户要求设计测试执行，不等于授权开始某个真实需求的测试。

## 一、用自然语言接入执行任务

用户可以说“QA 已经部署了，按这份全量用例开始测”或“先测一级用例”。Agent 先读取项目、需求、正式用例、已有运行和约定，判断是首次执行、继续未完成部分还是明确复测。不会要求用户再填写已有背景，也不会把继续误当重跑全部。

启动时给出简短说明，例如：

> 我先核对这轮用例、QA 环境和账号数据，确认关键操作可以执行后，从本期核心场景开始。每条都会保留实际结果和证据；受阻部分单独说明，不受影响的部分继续。

本轮执行上下文至少记录：项目与需求、任务／运行批次、用例及规则版本、选择范围、系统与环境、部署版本信息、角色与账号引用、准备数据和来源、允许的操作范围、证据及 BUG 位置、用例标记方式、清理与结束约定。部署版本确实未知时注明，不猜版本；会影响选择正确被测目标时须先补证。

新增、编辑、提交、审批、删除、上传、下载和数据恢复按用户已有执行范围处理；范围明确后连续推进，不每一步重复请示。范围不足、账号身份无法确认或动作涉及未授权对象时，只补当前必要信息。环境不可达不自行切到其他环境。

执行约定沿用优先级为用户本次要求、适用项目既有约定、本文默认值。工具“能操作”不等于目标和效果已获授权；只读任务不得为解除数据阻塞自动造数或改权限。开始前简短告知本轮采用的范围、方式和关键限制，不把这段说明变成对已经明确授权的重复确认问卷。

## 二、执行前准备与批次固定

1. 核对正式文件及当前未保存修改，按独立场景识别选择范围；不能把导图节点数当用例数。保存本轮用例版本、规则依据及场景标识，新增或退出范围另记变更。
2. 检查场景的业务预期、操作依据和实际执行条件。步骤尚未核实时先补采；缺规则回到澄清，缺数据或账号保留具体阻塞。已有团队评审要求也在此沿用。
3. 检查实际可用工具、浏览器／接口入口和需要的身份。能配置、工具可见、已连接、正确目标可用分别核对；已知且匹配的准备条件直接复用。
4. 为本任务隔离浏览器上下文与数据，核对实际账号、组织、角色和目标业务对象。不同标签页不自动等于会话隔离；同账号互踢、共享角色或单据需要协调。
5. 根据场景准备合法数据，记录真实 ID、关键值、创建来源、使用者和清理约定。可复用稳定的只读数据；会被修改或影响计数、历史、审批状态的数据按场景隔离。

本轮依据固定为用例／实例标识及版本、规则来源、环境与部署信息、所用模块版本和依赖摘要；每次尝试有独立标识并关联原场景。规则、页面或用例发生变化时，先记录影响和新的依据，不在运行中静默替换预期。等价步骤校准可在授权内继续，实质规则变化返回澄清。

数据优先选用能满足场景且不受其他任务修改影响的合法样本。需要写入时，在授权范围准备本轮专用数据并记录归属，不把“最新一条”当唯一标识，也不为加测试标识破坏本来要验证的输入。修改已有角色、权限或配置前保存必要原值与恢复方式；不能恢复或范围不明的部分先明确处理约定。

准备校验核对的是本条场景需要的身份、关系与状态，不要求所有账号都具有目标操作权限、所有测试输入都合法。权限拒绝、空结果和无效输入本来就是测点时，按用例构造和观察，不能提前替用户补权限、纠正负例数据或把它们一律当阻塞。

造数和配置修改必须在已有授权内。辅助准备可以复用已核验且获授权的接口或脚本，记录其用途；如果创建、登录或审批本身是测点，必须走被测路径。不能拿已完结咨询单作准备来替代从创建到审批结束的主链路。

不要求把所有环境、工具和数据准备齐才开始任意场景；能独立执行的范围可以先推进，缺口不得隐藏或删掉。

执行记录和证据归对应项目、需求的 `runs/<本轮标识>/` 或已映射位置，状态层保存可核对引用。正式用例仍留在用户原来的文件／工具中，结果按版本及场景关联，不复制成另一份相互漂移的用例。关键执行记录无法持久化时停止依赖它的新写操作，先处理存储阻塞；备份需覆盖已登记证据，不把仅存在于聊天或可清理缓存中的信息当作长期保存。

## 三、执行方式与分工

| 场景 | 执行规则 |
| --- | --- |
| UI 用例 | 强烈推荐 Chrome DevTools MCP，默认通过专用 headless Chrome 真实交互；先查可复用 UI 模块，没有合适模块时在同一隐式模式下观察并操作页面、保存路径 |
| 接口用例 | 依据已确认接口契约和用例构造请求，核对身份、请求、响应及相关业务状态；HTTP 状态码只是其中一项依据 |
| UI 与接口配合 | 网络或只读接口可辅助定位及核对约定的持久化状态；不能用直接业务写接口代替 UI 测点后声称 UI 通过 |
| 稳定重复交互 | 参数化调用固定版本模块、在关键位置回读，正常返回简洁回执，按需展开证据 |
| 陌生页面或失效模块 | 定向补采并判断变化，或使用实际可用的原生交互；不能猜控件、跳过检查或用旧通过证据冒充新场景结果 |

Chrome DevTools 的所有调用默认使用独立 headless Chrome，不显示或抢占桌面窗口，不接管日常 Chrome。只有用户明确要求显式执行时才允许可见模式，并记录适用范围；登录、验证码、上传下载或排障困难不自动构成切换许可。无法在隐式模式继续时说明具体阻塞，其他独立工作继续；展示截图不等于启动可见浏览器。

实际接入阶段先检查工具、宿主和依赖；未安装时帮助用户完成必要安装和 headless 配置，已安装且适用时复用。保留原有连接，新增或选择专用无界面入口；核对实际启动模式，不按服务别名猜测。系统权限或客户端加载确需人工参与时仅补必要操作。原工作台的模块经验可以复用，但不能把局部验证当成所有交互已支持；第 4 步落实实际适配，本轮不改配置或安装软件。

默认采用单一执行者顺序推进。项目已明确采用“业务大脑＋执行会话”时，前者负责规则、范围和结果审查，后者负责页面／接口动作、取证和运行记录；复用现有执行会话。新建会话、启动子代理、并行执行及跨会话消息需要相应明确授权和实际宿主能力，不能只因预期更快就自动派发。

并发授权、隔离条件和前置准备同时满足后，默认从 2 条独立场景开始，稳定后可逐步升至默认上限 4；用户或项目明确的环境预算可覆盖该默认值。这是保守的工程起点，不是已经测得的最佳并发量，后续按同条件验证调整。并发按独立场景计数，页面自然产生的请求量也要观察，不能将场景数直接当接口并发数。

同一业务对象、会话、权限配置或存在状态依赖的场景保持串行；共享存储、账号互踢或工具全局活动页使隔离不可证明时降为顺序执行，不声称仅有不同页签就足够隔离。跨角色主链路由一个任务负责或明确交接同一对象，不分成互不关联的并发片段。

出现串页、身份漂移、资源冲突或服务持续异常时，先停止受影响派发并降并发，保存已有结果；网络服务明确限流时遵从服务要求及任务预算，不增加重试来抵消阻塞。授权并发不自动授权压测、新开额外用户会话或另组代理团队。

模型和工具按项目配置，不把特定 GPT 型号固定给所有用户。实际执行者不重做需求分析，只读取任务范围、必要规则、用例和模块；有业务疑问带着具体证据返回主会话。多个执行者不得同时操作同一页面、单据或导图，正式用例结果投影明确唯一写入方。

## 四、安排顺序与每条用例的执行循环

先在授权范围核对一小段核心路径，尽早暴露部署、身份、数据或关键流程阻塞；随后继续全部选定范围，这段先行核对不是全量完成。按业务依赖和风险安排本期变化、少量完整主链路、必要分支／边界以及受影响历史回归，不为提速改变测点、数量或数据条件。

每条独立场景采用以下循环：

1. 核对本条准备、身份、数据与页面／接口起点，将场景登记为执行中。
2. 按本条步骤操作，保持场景内角色顺序与真实数据交接。调用模块前核对适用范围、副作用和固定版本；必要时真实观察后继续。
3. 在检查点读取实际结果，并按本条预期判断。关键写入前留存动作与回查线索，触发一次后核对结果；超时或断线先记录未知，不能重发试探。
4. 保存实际条件、动作、数据、检查结果与必要证据，判断整条场景结果及未完成步骤。
5. 失败或疑似问题建立可追溯的问题记录；按项目约定回写用例标记并核对保存，记录本条结束状态，再开始下一条。

若前面已经观察到明确业务失败，后面又无法继续，保留已证实失败及未执行步骤，不能将整条悄悄改成纯阻塞。某共同前置不可用时，受影响后续场景记录依赖阻塞，不重复执行同一无效路径；不受影响的已授权场景继续。

### 执行中持续保存页面信息并维护 UI 能力

用户补充希望在执行中保存有效页面信息，持续沉淀到项目 UI 模块。它是本规范的常规机制：真实执行也是取证来源，发现增量信息即保存，适合复用的部分在合适边界整理、验证和登记，不等待所有测试结束再凭聊天回忆。

| 有效信息 | 保存与复用方式 |
| --- | --- |
| 页面入口、页签、区域和目标记录定位 | 进入项目页面资料，关联实际环境、角色、业务状态及证据；可供后续步骤校准 |
| 控件名称、可用条件、联动、重绘和就绪信号 | 保存可观察条件与定位策略，支撑可靠等待和交互；不把当次快照 uid 或坐标当长期常量 |
| 主单、子单、卡片等数据交接 | 保存识别和绑定方法，模块使用参数；本轮真实值只进入对应运行记录 |
| 查询、打开详情、填写、展开历史、上传或下载等稳定片段 | 先查已有能力，再按契约形成候选实现或修订；验证后登记可复用范围 |
| 页面变化、失败条件或能力局限 | 保留实际现象、触发条件、影响及证据，补充模块限制或失效记录；不把异常沉淀成正确业务预期 |

采用增量处理：优先复用已有适用资料／模块；新发现与本轮步骤、页面和证据关联后及时落盘；每条场景或一组操作结束时整理有价值的变化；必要模块修复在安全边界处理，其余维护按批次或收尾推进，避免为完善模块库停下整轮测试。没有新增信息时不反复保存完整 DOM 和相同截图。

页面说明可以先保存为限定条件下的观察事实。人工／原生操作走通，只能证明该实际路径；新提炼出的代码必须按 UI 规范进行实现验证，不能直接沿用人工操作或另一个版本的通过记录。若本轮已经运行了相同实现、版本和依赖，且满足声明的模块验证检查，可引用本轮证据，无需为形式重复同样操作；覆盖不足则保留未验证范围。

一条业务用例失败，不代表其中已实际验证的查询或详情模块全部不可用；可保存有独立依据的成功片段，但整条用例仍保留实际失败结果。模块不得因追求复用而忽略业务异常、截短输入、放宽校验或修改用例预期。

更新使用新版本和可追溯来源，按适用环境、角色及状态核验；活跃场景继续固定其依据，不在组合流程中途热替换。新能力在适用验证完成后供后续场景或批次明确选用，记录本次引用。跨会话编辑明确同一模块的修改负责人，项目专属发现不自动推广到其他项目。

本轮执行记录是事实来源；提炼后的页面资料和能力进入项目 ui 目录或既有映射，验证记录引用本轮证据，索引按已完成内容生成。凭据、真实单号、私人内容和会话对象不进入公共实现。界面操作资料可持续本地保存，不受最终业务知识等待正式上线后进入 asynctest-kb 的时机限制；两者的来源、确认状态和目的分别维护。

进度或收尾简短列出本轮复用、新增观察、候选能力、已验证更新及仍待处理项；保存了页面资料不等于模块已经可执行，模块已验证也不等于整条业务用例通过。本机制尚未实现，本轮没有采集真实页面或修改实际 UI 脚本。

### 咨询单主链路示例

以下仅说明执行机制，实际角色和验收规则来自具体需求：创建人填写本期内容并提交，回读真实单据标识；实际审批角色按该标识找到同一对象，在相应节点核对本期内容及状态；走完必经节点到达定义的终态，再回查最终结果。

同一条主链路可以复用查询、详情、填写和提交模块，但每次身份、业务对象和关键结果仍核对。多个节点属于同一场景，不能把每个模块完成累计为多条用例通过。审批路由不清、接单人与审批人不同或目标记录不唯一时，先核对依据，不拿管理员或列表第一条代替。

## 五、业务结果怎样判定

采用以下面向用户的结果分类。它们是定稿的设计语义，现有 0.2.1 本地运行器尚未实现全部分类；后续适配需要明确映射，不能直接传入不支持的状态值。

| 分类 | 判定依据 |
| --- | --- |
| 未执行 | 本轮尚未开始该场景 |
| 执行中 | 当前正在进行，尚未形成最终判定 |
| 通过 | 所有必需步骤和断言已完成，必要证据齐全，实际结果符合有依据的预期 |
| 失败 | 已有明确实际结果与已确认预期不符，身份、数据和条件有效；根因可以继续分析 |
| 阻塞 | 必要环境、权限、工具、数据或依赖不满足，尚不能完成相应判断 |
| 待核验 | 写入是否生效不明、规则冲突、关键事实或证据仍待核实，不能先报通过或失败 |
| 跳过 | 用户明确要求或既有约定决定本轮不执行，记录原因，不算通过 |
| 不适用 | 根据本期规则或范围核实本场景不适用，记录依据，不能拿它隐藏执行困难 |

模块 completed、浏览器点击完成、成功提示或 HTTP 200 不能独立决定用例通过。负例中按确认规则拒绝提交，且数据状态符合预期，可以通过；正例观察到相同拒绝可能失败。脚本定位异常不自动就是产品 BUG，业务失败也不要求先找到完整技术根因才能记录。

用例结果、问题归因、BUG 状态、导图同步及数据恢复分别记录。通过须有必要证据；已证实失败可以有尚待补齐的 BUG 截图或正文任务，但不能声称 BUG 已完整记录或提交。

## 六、证据与用例标记

每条结果关联场景及版本、运行批次、环境／版本、角色引用、真实数据标识、操作或请求、预期与实际、关键检查点及证据路径。读取范围、未执行步骤和结束状态明确；网络请求／响应只保存必要内容，凭据和原始会话遵循本机存放规则。

正常路径保存必要的检查结果和关键状态，不要求每次点击都截图。UI 业务失败或探索发现保留至少一张能说明实际现象的真实截图，按项目规范添加标注并保留原图；必要时加网络或其他状态证据。生成式导航示意、控制台文本或接口返回不能冒充原始 UI 截图。截图缺失时保留缺口，不伪造。

上传要核对文件条目与最终保存，下载要核对实际浏览器操作、文件落地及内容；选中文件、存在 Blob 或另存网络响应不单独算原用例完成。权限、持久化和历史内容等结果按其业务要求回读，不只保留提交提示。

正式用例保存定义；运行记录保存执行事实，导图或表格的结果是相应批次的展示。Mind 可沿用项目约定的通过 100、失败 error；阻塞、待核验、跳过等使用当前工具实际支持且含义明确的标记或备注，不能全部写成 error。其他格式映射到对应状态字段，不强制改工具。

每条场景完成后立即持久化结果及必要证据，默认随后回写本条标记并保存／回读；工具确需合并提交时，只合并已经持久化的短批结果，持续保留待同步清单，并在阶段切换、暂停或收尾前尝试同步。不能将全轮结果仅保存在聊天中等最后一次写入。

窗口、修订或用户修改冲突时保留本地结果及待同步状态，核对后补写，不因为标记失败重跑已经完成的业务操作。旧执行标记不作为本轮结果；人工结果与 Agent 结果冲突时保留来源并核对，不静默覆盖。业务结果和待同步列表分别汇报，文件保存失败不能记为已回写。

若用户格式中的一个展示节点汇总多个已声明实例，全部必需实例通过才可标记该节点通过；有明确失败时展示失败并保留各实例的完成情况，没有失败但仍有未完成项时展示对应未完成状态。不能把单个实例成功写成整个节点通过，统计也不能混加节点数与实例数。

## 七、遇到问题怎样分流

| 发现 | 行为 |
| --- | --- |
| 清楚的业务不符合预期 | 保留失败检查点和复现证据，关联已有问题或建立本地 BUG 候选记录；必要归因继续进行 |
| 页面名称、位置或等价操作与用例不同 | 定向补采并修订受影响步骤／模块，记录版本差异；业务预期不变，有授权则继续，不自动报 BUG |
| 规则或预期不清楚 | 回到 3.1 澄清，说明影响；相应结果待核验，其他独立场景继续 |
| 工具、脚本或数据准备出错 | 保存执行问题，修复或列阻塞；不能伪装产品 BUG，也不能为继续而放宽测点 |
| 提交后结果未知 | 保存原操作、目标和关联信息，回查同一对象；无法确认则保持待核验，停止依赖该状态的后续写入 |
| 用例以外的明显问题 | 作为探索发现保留证据和影响，不虚增原计划用例数；新增正式场景按范围及修订流程登记 |

每条失败都关联 BUG、候选问题或明确的待分析原因。多个场景可以关联同一个经证据支持的问题，一条场景也可能发现多个独立 BUG；失败数不要求等于 BUG 数，合并必须说明相同原因及覆盖范围，不能只按模块名合并。

本地记录与外部提单分别处理。已有授权包含提交时按项目映射和 3.6 的实际提单能力继续，否则只保存明确状态的本地记录。技术归属没有证据时注明待归因，不随意指派；不得从旧项目复制人员和版本字段。修复验证另按用户触发或明确任务授权开展，不监测到“已解决”就自动重测。

### 重试与暂停的默认规则

- 等待页面就绪使用模块／工具声明的有界等待。只有明确可安全重复、且当前前置已核对的只读动作，才允许针对暂态执行故障自动重试一次；模块未声明可重试时仍不自动重试。原尝试与重试的事实、耗时及原因都保留，结果按完整观察及场景预期判断，不能把首次异常抹掉或用重试成功覆盖已证实的业务失败。
- 业务校验拒绝、已确认的规则不符合、身份不符或作用不明的请求不按网络暂态故障重试。写入不会因超时自动重放；修复定位后也须先核对原操作是否已生效。
- 单条数据、页面或前置阻塞只暂停依赖它的场景，其他独立范围继续。环境或身份整体不可信、关键记录无法持久化、共同工具已不可靠、用户明确暂停时，停止相应范围的新动作并给出原因；不是一遇问题就结束整轮，也不是带着未知条件继续写入。
- 达到用户约定的时限、资源或调用预算时停止新派发，保存进行中事实并交付未覆盖项；不通过缩范围、修改预期、重置计时或重复计数伪装完成。没有固定适用于所有需求的统一时长。

## 八、中断、恢复和资源处理

用户暂停时停止派发新动作，保存进行中场景、证据、数据标识、当前页面与身份、已发出未核实动作、待同步标记及占用资源。暂停不要求先把未知动作改成成功或失败，也不声称已强制停止无法控制的外部进程。

继续或换会话时，先定位同一批次与断点，核对用例、部署、模块版本和现场身份是否仍适用，确认原执行者已停止。未知写入优先回查；从明确未完成的地方接续，不重跑全部，不复制另一角色的登录态，不把历史通过自动套到新版本。

回查记录关联原动作及后续核实依据，保留原始未知事实，不重写成当时已经收到成功回执。明确未应用后是否重试，也按本轮授权、当前前置条件和可用证据决定。

关键写入以本轮动作编号关联目标、输入版本、调用者、时间和可回查线索。回查“暂时没查到”不能直接视为未应用，要考虑查询身份、筛选、异步处理和实际一致性条件。只有证据足以确认未生效且再次执行不会重复产生结果时才可重试，否则继续保留待核验。一次唯一且上下文吻合的权威回查可以补足结果，不需要再创建一条来验证。

清理仅针对本轮创建或明确指定的数据／配置，按约定恢复并回读。需要保留复现数据时记录用途和处理责任；不能为保持“干净”删除 BUG 证据或其他任务数据。恢复失败、共享数据仍在使用和无法回退的状态单独交付，不虚报已还原。

默认在既有授权内恢复本轮临时权限、角色和配置，按保存的原值核对；业务测试单据按事先的保留／清理约定处理，默认不额外发起批量删除。若需留作复现或后续场景输入，记录保留目的和后续处理。恢复本身是用例测点时纳入业务判定；仅属于环境善后时保留已经验证的业务结果，同时单列恢复未完成，不能因此声称全部收尾完成。

恢复前核对当前对象和变更仍属于本轮，且没有被用户或其他任务进一步修改；出现冲突时保留原值、当前值与归属记录并协调处理，不能仅凭旧快照覆盖别人后续的有效修改。

## 九、进度和结束交付

在活跃执行期间，每完成一组或约 3—5 分钟给出可核算总体进度，关键失败、未知写入、需用户参与或范围变化及时说明；实际宿主的更短反馈要求优先。这是工作中的反馈频率，不是后台唤醒承诺。

本轮总数按独立场景／参数化实例及版本固定，状态互斥汇总：未执行、执行中、通过、失败、阻塞、待核验、跳过、不适用之和应等于本轮范围。重试和复测以独立尝试／批次记录，不重复累计同一场景完成数。范围变更说明前后差异，不能悄悄改分母。

BUG 数、探索发现、待同步条数和数据恢复情况另列，不混入用例状态总数。用户能看出哪些结果已有证据、哪些缺数据、哪些等待判断，不能把所有未完成都归为环境阻塞。

保存批次内唯一场景集合及最新尝试指向，重试仍保留原尝试而不增加场景分母；新增、删除或变更实例范围记录修订及原因。每条失败都核对问题关联，每条通过都核对必需断言和证据，每条跳过或不适用都核对依据，公共准备和单个模块完成不额外计入场景数。

结束时提供用例及批次入口、实际执行范围与结果、失败和问题关联、未测／阻塞／待核验项、标记同步与数据恢复情况、下一步。默认不额外生成成套报告，用户指定报告或测试计划表时再按目标范围交付。

全部目标已逐条核对并保存结果后，才能报告实际执行完成范围；有失败或阻塞时不能说全部通过。有未知写入、未执行场景或未保存证据时如实列明未完成，不用预算、工具完成或会话结束冒充需求验收。最终知识沉淀仍等正式上线和短期稳定确认。

## 定稿记录与后续实施

用户在已明确默认隐式浏览器、自动接入与执行中 UI 沉淀后，将剩余执行规则交由 Agent 决定。本文件据此定稿，下一项为 3.6 BUG 记录与提交设计；不需要用户重复确认同一批已委托的细节。默认值可由具体任务和项目明确约定覆盖，历史结果及事实边界不可通过改默认值重写。

先完成所有业务环节设计，再落实工具适配、实现和集中验证。本轮没有实际安装浏览器、执行用例、建会话或提交 BUG；先前另行授权的具体业务任务不由本次设计改写或重新调度。

后续实施与验收需覆盖：缺模块仍能通过实际工具执行、真实业务断言、负例拒绝、整链路不跳过被测动作、步骤差异与 BUG 区分、失败与 BUG 多对多关系、标记失败不重跑、未知写入恢复、并发资源冲突、数据恢复和可核算进度。合成运行器验证、真实浏览器／API 验证、目标读者可见性和完整业务验收分别记录。
