# 3.3 测试用例编写与修订设计 v1

日期：2026-11-02。状态：按用户明确要求及“你来决定这三件事情”的授权，由 Agent 对场景生成、增补修订和编写完成依据决策定稿，形成完整 3.3 设计基线。用户特别要求充分理解业务、受控覆盖历史需求，并保留少量从创建到审批结束的完整主链路；本规范将其纳入编写规则。设计定稿不等于已写入 Skill 包或经过真实需求验收，本轮不创建真实用例、不操作 Mind 或配置 MCP。

## 用户明确要求

1. 强烈推荐使用 asynctest-mind MCP 编写、维护思维导图用例，并提供自然的接入引导；用户可以提供 MCP 配置截图作为指引素材。
2. asynctest-mind 是推荐工具，不是硬性前置；未使用该工具也应能推进用例工作。
3. 提供一个默认推荐用例格式；用户指定自己的格式时沿用，不能强制替换。
4. 无论采用什么格式，都明确向用户说明并补齐操作步骤。步骤结合页面采样信息，成为指导测试执行、BUG 复现及后续验证的重要依据。
5. 场景生成必须建立在充分业务理解上，不能泛泛套用通用测试清单；可控地编写与本期有关的历史规则回归。涉及流程的改动保留少量完整主链路，例如咨询单创建内容变化时，覆盖从创建到审批结束，不能完全没有这类用例。

本轮三项决策：场景以业务规则及影响链推导，采用本期变化／受影响旧规则／少量完整主链路的覆盖检查；增补修订按影响关系维护最小必要变化并保留历史；完成依据分别判断内容可评审、操作已核对、执行准备就绪。以下规则为设计基线，用户的明确项目范围和格式要求仍优先。

本阶段承接 [需求分析](requirements-analysis.md)、[各阶段按需取证](page-discovery.md) 和 [UI 模块规范](../ui-modules.md)。步骤描述动作，预期提供有来源的判定标准，两者不能相互替代。

## 编写交付与评审的关系

用户于同日后续确认：用例编写完成就应可以直接拿去评审，无需在 Skill 中单独设置“用例评审”必经环节。原 3.4 的质量自查与反馈修订并入本阶段；Agent 在交付前核对业务、覆盖、主链路、步骤与可读性，收到评审意见后按增补修订流程处理。

团队实际组织评审的方式照常遵循，需要时可辅助讲解或整理反馈；是否已评审只按实际记录，不由编写自查推断，也不默认给所有项目增加执行门槛。项目明确要求评审通过后才能测试时沿用已有约定。后续执行准备与执行见 [测试执行草案](test-execution.md)。

## 一、怎样推荐工具并引导接入

首次需要确定用例载体时，先读已有项目约定及正式文件。用户已选工具或有可用连接时直接沿用，不反复推荐或要求重新配置。

建议话术：

> 我强烈推荐用 asynctest-mind 来维护思维导图用例：评审时可以先看业务分组和场景，执行时再展开步骤与预期，Agent 也能通过 MCP 读取和修改同一份内容。如果你们已有表格、文档或其他用例工具，我会沿用现有方式。

说明的是推荐工作方式，实际编辑、转换和标记能力仍以当前工具为准。工具可见不等于已经接入用户目标文档或保存成功。

Mind 未接入时，可先用用户认可的载体整理同一套场景内容。用户明确要求最终交付 Mind 时，中间文本只是草稿，导图交付仍待完成；不得把换格式说成已完成指定交付。其他格式无法直接编辑时说明能力缺口，提供可审阅内容或可用的交接方式，不声称支持所有客户端和文件格式。

接入指引应展示用户从实际应用何处取得 Mind MCP 信息，由当前 Agent 核对自己的宿主与配置能力并适配。用户已于 2026-11-02 提供三张截图：AsyncTest 首页进入 Mind、点击 MCP 配置、stdio 配置弹窗。已形成 [三步图文指引](../integrations/asynctest-mind-onboarding.md)，采用蓝紫色标注并模糊个人及最近文件信息。可见字段为服务名、Command、Args、Env，按用户自己页面复制；不把 asynctest-kb 的地址套给 Mind。素材尚未加入发布包，实际配置与新会话图片展示仍待验证。

仅问“Mind 是什么、怎么获取配置”时先解释，不自动安装、连接或改文件。已获接入授权时按实际能力处理，只把确需用户参与的步骤交回用户，不反复请求同一授权。

## 二、格式优先级与必须说明的操作步骤

采用顺序：用户本次指定格式 → 适用项目／团队现行模板 → Skill 推荐格式。先从现有资料识别，不让用户重复提供已有模板。

展示结构可以不同，执行信息应能对应到场景的准备条件、操作步骤和预期结果。用户模板中的“前置条件”“测试步骤”“检查点”等等价字段直接映射，不为统一名称强行改表头。

Agent 应明确说明：

> 我会沿用你的用例格式，并把每个场景的操作步骤补齐。步骤会写清谁、在哪个页面、对哪条数据、做什么；后面执行测试、复现 BUG 和验证修复都以这些步骤为依据。页面还没部署的部分会标明待核对，部署后再补采校准。

模板缺少步骤时，优先在现有文档中用步骤列、子节点或备注承载；如模板限制无法判断容纳位置，集中说明缺口并确定合适位置，不擅自破坏模板。允许有明确、可打开的关联步骤记录，但不默认另建一份独立维护的“执行版”。只有标题或摘要的产物不能标成步骤完整、可直接执行的用例。

用户只想在评审时看标题，可以折叠步骤或展示同一来源的摘要，执行细节仍保留。新增要求与实际授权范围分别处理，不借补步骤扩写其他需求或执行测试。

## 三、默认推荐结构

默认沿用已使用过的独立场景范式，并将作者、版本及日期等项目取值参数化。以下为结构示意，不是实际业务规则或已经生成的用例：

```text
需求概述
└── 需求概述（需求编号）
    └── 业务分组
        └── 场景标题：具体条件／动作＋核心预期
            ├── 准备条件
            ├── 操作步骤
            │   ├── 1、页面动作
            │   ├── 2、页面动作
            │   └── 3、页面动作
            ├── 预期结果
            │   ├── 步骤2：可核对结果
            │   └── 步骤3：可核对结果
            └── 结束处理（仅实际需要时）
```

- 一条场景可以独立判定，按业务过程分组，标题让首次阅读者也能解释测什么。正常、异常、边界、权限和状态作为覆盖检查维度，不机械制造多层分类或凑数量。
- 各场景步骤从 1 开始；同一场景跨角色保持连续编号。1、2、3、4 是编号方式，不要求恰好四步，不把整个需求压成一条长流程。
- 每一步直接写动作，避免再嵌套“步骤标题→操作→应看到”。预期对应本场景关键步骤号，不强行为每次无独立检查点的点击生成一条结果。
- 准备条件包含角色、起始位置、业务状态、数据及取得方式；公共准备可以明确引用，不使用“同上”“合适账号”或“最新一条”掩盖缺失条件。
- 表格格式可映射为场景标题、前置、步骤、预期等列；用户有自己的格式时不要求遵守上述节点层级。
- 若用户采用默认 Mind 命名，可推荐 `{版本号}版本_{需求概述}_{作者简称}_{发版日期}.amind`；字段按项目约定，不把 lb、20261030 或某个旧版本固化为所有用户的默认值。缺必需信息先整理内容，不猜版本或用创建日期冒充发版日期。
- 根节点、需求节点与编号以实际已知需求和用户模板处理；缺少编号不伪造，也不因此阻止业务内容整理。

工具选择、字段承载及推荐格式只在确有缺口或首次需要时讨论。已有明确范式直接复用，不每个需求重复确认样式。

## 四、步骤怎样支撑执行

步骤以“平台／角色＋页面或区域＋目标控件／数据＋动作＋输入”说明实际操作。紧密且目的明确的动作可以合并一句，角色切换、重要跳转和独立检查点清楚分步。界面名称来自当次适用的页面证据，不能用定位器、坐标或模块 ID 代替人可读步骤。

例如“在咨询列表查询并打开准备条件中记录的子单”还需依据实际页面补足输入框名称、查询动作及目标行操作。具体文字由取证决定，不把本示例当作真实控件确认。

步骤信息应满足：

- 目标唯一：跨角色使用前一步真实回读的单号、卡片或业务标识，参数能追溯取得方式。
- 数据明确：区分固定测试输入和执行时绑定的真实值；附件有文件来源、内容及准备方式，不凭空使用不存在的文件。
- 顺序可执行：前一步输出能供下一步使用，页面未就绪或身份不符时有明确边界。
- 预期可判定：来自需求或已确认规则，包含关键文字、数据、状态和观察位置，不只写“正常”。
- 写入有回读：成功提示、HTTP 200 或完成某个模块不能单独替代实际保存与业务状态。
- 终点明确：达到场景目标即停止，必要时写清数据和页面结束状态，不顺带审批或删除其他记录。

接口场景的步骤对应已确认的请求、数据交接和响应检查，不强行编造页面动作；具体接口执行适配仍在后续工具设计范围。

BUG 复现与修复验证可以引用本场景的条件、动作、预期及证据，但不能仅凭步骤完整就声称执行通过；BUG 正文仍要据实际复现简化。业务严重程度还需要影响依据，不能由步骤数量推断。

## 五、取证与模块怎样进入用例

旧页面＋新需求可以形成用例草稿；首版无页面时按需求和原型形成暂定操作。记录旧页面实查、需求规定、推导和新页面实查的来源，关键未核对操作让执行者可见，不因为没有 QA 就阻止编写全部内容。

页面可访问、新增场景、角色变化或实际交互与步骤不一致时，按 3.2 定向补采受影响部分。纯操作名称或顺序差异可以修订步骤；业务行为与规则冲突时回到 3.1 澄清或按适用流程记录问题，不改预期迁就实现。

UI 模块映射记录于场景／步骤关联中，包含固定版本、范围及副作用。正文继续写清页面动作，模块仅加速复用；模块返回实际结果，由用例预期判断。模板转换不得丢失这些关联或把已有执行标记复制到新增场景。

## 六、从业务理解生成场景与受控历史回归

### 6.1 生成前先建立业务依据

先读取 3.1 的本期变更、业务对象与关系、主体资格、数据归属、状态流转、规则来源及适用历史，不从页面字段名直接套“正常、空值、超长、特殊字符”清单。

对每个本期变化，至少能解释：谁在什么业务条件下处理什么对象；哪项规则改变、哪项继续沿用；相关数据和状态会传给谁；结果在哪里、按什么依据判断。沿本期数据和状态的使用方向定位依赖，必要时补查上游约束、下游处理和既有缺陷。历史查询在足够支撑这些条件与预期时停止，不扩展成整个系统知识整理。

当组织归属、角色、单据状态或内容版本共同决定结果时，按实际关系设计合法对照，说明保持什么不变、改变什么；不能把业务上不存在的组合当测试数据，也不能从“一类主体允许”直接推断“其他主体全部禁止”。需求理解体现为这些有依据的条件与结果，而非只把字段名替换进通用模板。

每个场景在轻量覆盖记录中关联：需求／规则来源、业务目标或风险、触发条件和变量、预期及观察位置、涉及的页面／角色／状态、历史依赖、所属覆盖目的。无需另生成一套报告，也不把内部来源编号塞进评审标题。

不能解释业务作用或判定依据的场景，先补理解或作为待确认候选；不能用“正常”“符合预期”掩盖规则缺口。通用输入、兼容性、权限或健壮性检查只在与本次变化、项目既有规范或具体风险有关时纳入，并写清实际条件和结果；不因它常见就批量铺到每个页面，也不因此漏掉确实适用的基础校验。

### 6.2 三类覆盖共同检查

| 覆盖目的 | 选择依据 | 咨询单创建内容调整的示例方向 |
| --- | --- | --- |
| 本期变化 | 新增／修改规则、合法与不合法条件、规则分支及明确边界 | 新内容怎样填写、保存和提交，哪些条件决定接受或拒绝 |
| 受影响的既有规则 | 本期改动可能影响的上下游数据、状态、权限、计算或历史缺陷 | 旧有单据归属、实际审批人、内容读取或退回处理是否仍满足适用规则 |
| 少量完整主链路 | 将改动放进真实业务流程，验证关键交接和最终业务结果 | 以本期内容创建咨询单，提交并经过实际审批路径到达审批终态，再按规则回查结果 |

这三类用于覆盖检查和选择原因记录，不强制变成导图的三层抽象分类。展示仍沿实际业务过程分组。

涉及有实际生命周期的流程改动，默认至少保留一条适用的完整主链路；通常先选代表性的正常路径，有实质不同的业务规则、审批路由或高风险状态路径时再增加必要的链路。不能将“少量”解释为零条，也不对每个角色、字段、机型或输入组合复制一条全流程。

单纯无业务流转的独立功能不编造审批流程，可选择从入口动作到可核对最终结果的闭环。用户明确限定或排除的范围仍应遵守；若必要主链路穿越被明确排除的范围，说明覆盖缺口及影响，由范围决定处理，不能静默扩大或隐藏缺口。

历史规则优先读取已有记录与可用知识库，核对本期仍适用的版本；历史用例只作为选取线索，不复制旧通过标记或直接照搬旧预期。每条旧规则回归都能说明“为何这次改动可能影响它”；没有相关影响的旧功能不加入全量回归。

### 6.3 完整主链路怎样写

以下是设计示例，具体组织、审批节点和结果必须由本需求材料确定，不将它当作真实项目的已确认流程：

> 正确主体为合法项目创建咨询单，填写本期调整的内容 → 提交并回读实际单据标识 → 按已确认的实际角色与节点流转 → 到达审批结束状态 → 从已定义的结果入口核对最终状态及本期内容。

主链路至少保留与其目标相关的检查点：

1. 创建及提交后的内容实际保存，单据身份与业务归属正确。
2. 交接到下一角色的是同一业务对象；该角色取得的本期内容与状态符合规则，允许的转换有明确依据，不能仅检查是否能点到下一页。
3. 必经审批节点能够依据相关内容继续处理；不以管理员代替所有实际审批人，也不跳过本次要验证的流转。
4. 到达明确定义的审批终态，回查最终内容、状态和本期涉及的不变约束；不虚构“结束后不能修改”等未确认规则。

主链路的创建、提交和必经审批必须体现在待执行步骤或可明确展开的公共流程中，不能把“已有一张审批结束的单据”放进准备条件后只看详情，就声称覆盖了完整流程。允许复用已定义模块来提速，但保留被测动作、关键检查和真实标识；通过接口直接造出终态数据不替代 UI 主链路执行。

若改动涉及退回编辑、再次提交、历史内容或不同审批路由，再保留有理由的一条关键分支到其终态；不把所有异常和边界塞入正常主链路。多个咨询类型是否可选代表路径，需要有规则与链路等价的依据，不能仅凭页面相似就认定等价。

完整链路是一条以端到端业务目标为核心的独立场景，可以跨角色并包含必要的多个步骤；它与本期局部规则场景并存，不取代后者，也不把整项需求压成一个泛化长流程。主链路有多少个检查点都仍是一条场景，失败时保留具体节点与证据，不能把各节点都计为独立用例通过。

缺少审批规则、角色、数据或 QA 页面时仍保留主链路设计及明确缺口，按影响标为待澄清／待取证／待准备；不得为了交付漂亮统计而删除它。设计这条链路不代表已经执行，也不自动授权真实审批或造数。

### 6.4 控制数量的规则

- 用不同规则分支、业务结果、状态迁移和实际风险决定场景，不为凑条数做所有条件的笛卡尔积。
- 相同触发、规则、预期和风险的重复场景合并或选代表值；输入只是字面不同且业务等价时不重复铺开。等价判断需有依据。
- 条件导致不同业务结果，或需要独立判定及追踪失败时拆场景；复杂参数化不得掩盖独立判定需求。
- 公共导航与准备过程复用，具体场景仍保留本身测点和必要交接；不能为省步骤跳过被测行为。
- 单点规则和端到端链路检验不同风险，不能因为经过同一页面就去掉主链路，也不反过来认为一条全流程已覆盖全部规则。
- 不设固定总条数、覆盖比例或主链路数量上限。每次新增应能说明新的覆盖价值；收尾能说明本期范围、关联回归和主链路的覆盖及缺口。

## 七、编写流程

1. 读取本期范围、已确认规则、待确认项、已有正式用例和用户格式，区分新增、增补或修订。
2. 按业务规则及影响传播推导独立场景，建立本期变化、受影响旧规则和少量完整主链路的覆盖关系；检查必要异常、边界、权限、状态和跨端差异，不根据现有导图剩余节点缩小范围。
3. 明确本轮工具和格式；已有选择直接沿用，需要时说明 Mind 推荐及操作步骤的作用。工具接入不成为无关业务分析的硬前置。
4. 将业务条件与页面依据结合编写准备、步骤和预期。规则缺口回到澄清，操作缺口按需取证；未部署部分保留草稿与补采条件。
5. 对新模板或粒度有实际歧义时，先用一条普通和一条跨角色示例校准再展开；已有用户确认且内容明确时不增加重复审批。
6. 在用户授权目标内写入或修订，保留现有修改和历史版本；保存后核对结构覆盖、受影响场景及步骤、格式和元数据。
7. 交付可直接拿去评审的用例、文件入口、完成范围及待确认／待取证项；评审反馈按本阶段修订处理，之后按任务授权推进执行准备。已编写、已保存、实际已评审和已执行分别记录，不再强制进入独立 3.4 阶段。

正式产物是一份可追溯的用例来源及必要关联，不默认产生多份相互独立维护的评审版、执行版和报告。格式切换属于显式变更，保留转换前版本并检查内容和关联，不把格式转换成功视为业务覆盖完整。

## 八、Mind 操作与保存

以下依据本轮可见的 MCP 工具说明，不表示已经调用或验证目标文档；其他工具采用其实际能力和等价检查。

确认唯一目标文档／窗口及当前内容，先读大纲，再按需读取受影响子树，避免反复加载全图。按实际版本的修订保护批量编辑并保存；大型新增与混合修改选择适用工具，不能用旧磁盘文件覆盖已打开窗口中的未保存内容。

未知写入结果先查操作状态和目标内容，不重复新增同一场景。保存后按全范围结构与实际修改内容定向回读，留意截断／分页；节点总数不等于独立用例数。工具要求的控制状态与结束连接流程按其当前说明处理，不推断未提供的宿主能力。

历史真实结果保留原场景版本和证据。表达修订不清除原事实；条件、步骤或预期实质变化时记录新版本与复核范围，新场景保持未执行，不继承旧通过标记。其他会话的修改和用户已明确停止修改的资料不被本轮覆盖。

## 九、增补与修订

新增需求、临时追加场景、历史规则澄清、QA 部署、页面变化或模块更新时，按以下过程处理，不重写整份用例作为默认动作：

1. 读取最新需求结论、正式用例和当前未保存修改，确认变更来源与本轮授权范围。
2. 沿“规则／页面／模块→场景及步骤→关联回归与主链路”找影响。新增条件是否已经覆盖、是否改变预期、是否需要新的流程分支，逐项判断。
3. 缺业务依据回到 3.1；缺页面操作依据定向补采 3.2；清楚的未受影响部分继续推进，不要求用户重述全部背景。
4. 最小必要增补或修改，保留原格式、稳定场景身份、来源和版本。合并或退出活跃范围时保留原节点映射与历史依据，不覆盖其他会话或用户未完成的修改。
5. 核对覆盖、步骤、数据交接、预期和模块引用，再保存回读。简短报告新增、修订、退出当前范围的场景及原因、关联主链路与仍待处理项，不默认输出成套变更报告。

| 变化 | 处理与结果保留 |
| --- | --- |
| 仅文字、排版或等价表达，未改变条件、动作和判定 | 保留适用的历史事实与引用，记录表达修订，不无依据地重置全部执行结果 |
| 条件、动作顺序、权限、数据、业务预期或关键检查改变 | 形成新版本，指出受影响范围及复核需要；旧结果继续绑定旧版本，不默认成为新版本通过证据 |
| 新增场景或流程分支 | 按独立目标写准备、步骤及预期，新场景保持未执行，不继承复制节点的完成标记 |
| 页面名称或布局改变 | 修订受影响操作和页面依据，业务预期保留其来源；如实际业务行为冲突，另行澄清或记录问题 |
| 历史规则被修正 | 同步其引用场景与主链路，标记关联执行结论和 BUG 需要复核；不自动重测、关闭工单或写知识库 |

已归档、明确停止修改或本轮范围以外的资料不因通用规范更新自动改写。模块变更沿用固定版本及验证范围规则；用例修改不自动触发 UI 执行或写入操作。

## 十、编写完成与就绪依据

分别记录三个维度，不把它们压成一个“完成”标记；评审结论和真实执行结果继续独立维护：

| 维度 | 达到的条件 |
| --- | --- |
| 内容可评审／本轮编写完成 | 授权范围及必要关联回归有对应用例，适用的完整主链路已包含；规则、条件和预期有依据，场景独立、格式适配、步骤逻辑完整，保存回读通过，缺口与来源明确 |
| 操作已核对 | 相关关键操作有适用于目标环境、角色及状态的真实页面依据；没有被推导动作冒充实查；不要求此时每条执行用单据都已准备好 |
| 执行准备就绪 | 内容及操作满足执行要求，本轮环境、实际角色、业务数据、工具、权限和操作授权已核对，待核实写入或资源冲突已处理 |

没有新页面时，依据确认需求写出的操作可以进入可评审稿，并明确“操作待取证”；不能标为已核对或无人值守可执行。有关键业务预期未定时，受影响部分仍为草稿／待澄清，只交付实际完成的范围，不能把整个需求宣布编写完成。

编写交付前进行业务自查：

- 每个本期变化能定位到规则、场景和可判定预期；不会只剩“创建正常”“审批正常”等泛化标题。
- 关联历史回归有选取理由，适用的完整主链路不是零条，新增分支的价值说得清；明确范围限制与尚未覆盖部分。
- 独立场景有可取得的准备条件、编号动作、目标及数据交接、对应预期；重复场景已检查，必要闭环没有因去重被删掉。
- 用户格式与所选工具受到尊重，推荐 Mind 不成为硬前置；关键待取证步骤可被执行者识别。
- 正式目标文件已保存并按范围回读，节点数量不冒充用例数，新增或改动场景没有错误继承通过标记。

交付仅需文件入口与版本、完成及未完成范围、选取的历史回归和主链路概要、关键缺口及下一步。自查后交付可评审内容，按团队约定处理实际评审及反馈，不自行标记已评审或测试通过；知识正式入库仍按上线后稳定确认规则处理。

## 定稿记录与后续验证

用户在已明确工具、格式和步骤要求后，将场景生成、增补修订、完成依据三项交由 Agent 决定，并特别强调业务理解、可控历史回归及少量完整主链路。本文件按该授权定稿；后续又确认取消独立评审环节，下一项改为测试执行设计，不要求用户重复批准已经委托决策的事项。

后续验证除原有工具可选、模板适配、步骤、取证和跨角色场景外，还需覆盖：没有理解旧规则时不会生成假预期；创建内容变更能推导到审批终态的检查；不相关历史功能不会被批量纳入；相同主路径不按输入组合重复膨胀；流程分支差异有理由地新增；未部署或缺数据时保留主链路及缺口；修订保留历史结果；可评审、已取证、可执行、已评审及已通过的状态不混淆。

上述为设计和未来验收要求，尚未实施完整用例生成器、实际编写咨询单用例或执行审批流程。
